# ocr — provenance, attribution, and what this corpus CANNOT tell you

A manufactured scan, the vector page it was made from, and the answer key that
falls out of the pair. Generated by `tools/gen-ocr-fixtures.py`; scored by
`tools/ocr-accuracy.py`.

## Source material and licence (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** `LEGAL.md` §5 category (a):
wholly synthetic, authored for this project, generated by a committed script
from geometry and words this project chose. **No real document — scanned or
otherwise — was involved at any stage**, and nothing was downloaded from
anywhere.

That is the entire reason this corpus exists in this shape. Project rule 7
forbids checking in a real-world PDF of unknown provenance, and a real scan is
exactly that, so OCR accuracy went unmeasured from `Pass 71.0` (2026-08-12)
until `Pass 129.0` (2026-08-25) — during which the engine was **completely
broken and nobody could tell**.

## What each file is

| file | what it is |
|---|---|
| `printed.pdf` | the vector original: known words, real Std-14 Helvetica metrics. **The answer key, not a test input** |
| `scan.pdf` | `printed.pdf` rendered at 200 dpi, degraded, wrapped as one full-page image. **Zero text objects** |
| `scan_clean.pdf` | the same wrap with no degradation — the control that separates "OCR is weak" from "the degradation is too harsh" |
| `scan_rotated_90.pdf` | byte-for-byte `scan.pdf` plus `/Rotate 90`, applied with pdfcer's own `rotate-page` |
| `GROUND_TRUTH.json` | every word and its page-space rect, extracted from `printed.pdf` by pdfcer itself |

## Why the ground truth is trustworthy without anyone typing it

A downloaded scan gives a picture and **no answer key** — somebody has to
transcribe what it says and eyeball where. Here the vector original *is* the
answer key and it is machine-readable: `find-text` on `printed.pdf` reports
where a word is, from real AFM metrics through the extraction path `Pass 4`
already tests.

So the two rectangles being compared arrive by **completely different routes** —
font metrics on one side, a neural recogniser looking at pixels on the other.
Their agreement is a result rather than a tautology (`R215`: never assert
against a blessed copy of your own output).

It scores **content and position separately**, and that split is the point: a
text layer can read every word perfectly and land mirrored, offset or
transposed, and **a mirrored layer scores 100 % on content**. Position is the
failure an operator actually reports and the one a word count cannot see.

## ★★ WHAT THIS CORPUS CANNOT TELL YOU — read before citing a number from it

**It cannot rank rasterisation resolutions, and it must not be cited as
agreeing that any DPI is better than another.**

Measured 2026-08-26, sweeping `scan.pdf` through `pdfcer ocr`:

| dpi | 72 | 100 | 150 | 200 | 300 | 400 |
|---|---|---|---|---|---|---|
| content recall | 100 % | 100 % | 100 % | 100 % | 100 % | 97.9 % |

**It saturates.** Every value up to 300 is a perfect score, so the corpus has
no power to discriminate between them.

That is **by design, not a defect**: the generator's own docstring says the
degradation is *"deliberately mild… It is not a stress test of the recogniser's
tolerance for bad input. A fixture degraded until recognition fails proves
nothing about pdfcer and would turn every future run into an argument about the
noise level."*

★ So this corpus proves the **pipeline** — that a page of ordinary printed text,
scanned, comes back readable and in the right place. It does not measure
**difficulty**, and a 100 % here is not evidence that a setting is well chosen.
When `pdfcer ocr`'s default DPI moved from 300 to 150 on 2026-08-26, the
evidence was `pdfce-gui`'s scored CAD sheet, and this fixture is explicitly
**not** cited as corroboration.

A corpus that scores 100 % on everything is not a corpus that agrees with you.
It is one that has not been asked a question it can answer.

## What is deliberately NOT modelled

Named so nobody assumes they were tested: JPEG artefacts, dust and speckle,
bleed-through from the reverse side, staple shadow, page curl, handwriting,
non-Latin scripts, multi-column layout, rotated *text* (as opposed to a rotated
page), and small type. **Handwriting in particular is out of distribution for
`ocrs`, which is a printed-text recogniser** — a poor result on handwriting is
expected behaviour and not a defect.

Harder cases belong in their own files, added deliberately, each with its own
recorded expectation.

## Determinism

The noise is a fixed-seed xorshift64\*, not `random`, so the files are
byte-identical on every machine and every Python version. A fixture that
changed between regenerations would make every measurement incomparable with
the one before it, and a regression would be indistinguishable from new noise.

## How to regenerate

```
python tools/gen-ocr-fixtures.py     # needs a built pdfcer
python tools/ocr-accuracy.py <an OCR'd copy of scan.pdf>
```

The script is the authority; these files are its output and are checked in only
so that `cargo test` and a scoring run need no Python round-trip through the
renderer.
