# mesh-ink — provenance and attribution

Single-page PDF fixtures pinning that **a mesh shading and a flat fill of the
same authored `DeviceCMYK` ink render the same colour**. Generated by
`tools/gen-mesh-ink-fixtures.py`; used by
`crates/pdfcer-render/tests/mesh_ink.rs`.

The mesh counterpart of `fixtures/synthetic/shading/`, which pins the same
property for *analytic* shadings. The two directories are deliberately
separate: they were fixed in different Passes, they fail for different
reasons, and a single directory would hide that a mesh has no `ColorRamp` to
carry colorants in.

## Source material and license (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** These are `LEGAL.md` §5
category (a): **wholly synthetic**, assembled byte by byte from ISO 32000-1's
own object syntax by a committed script — Table 79 for the shading
dictionary, Table 84 for type 4's vertex records, Table 85 for type 6's patch
records. No attribution is owed or claimed, and nothing was downloaded from
anywhere.

**★ In particular, no byte and no structure of the licensed print-conformance
suite is reproduced.** That suite is where the operator *saw* the defect, and
it is not redistributable, not in this repository, and not present on a fresh
clone or on CI. These files are deliberately **not** a reconstruction of it:
different colour, different page size, no reference image, a **flat** colour
where that suite uses gradients, and types **4 and 6** where it uses type 7.

The mesh streams are `FlateDecode`d (a mesh stream is binary by construction
and there is nothing to read by eye either way), but the file structure around
them is a classic §7.5.4 cross-reference table with no object streams, so a
failing assertion can still be walked in a hex editor.

## The two files

Both are 300 × 100 pt and paint the **same colour three times**:

| x range | what |
|---|---|
| 10–90 | a flat filled rectangle — the control, never bridged |
| 110–190 | a **type 4** free-form Gouraud triangle mesh (two triangles) |
| 210–290 | a **type 6** Coons patch (one patch) |

| file | page group | what it pins |
|---|---|---|
| `mesh-vs-fill-cmyk.pdf` | `/Group << /S /Transparency /CS /DeviceCMYK >>` | on a page that composites in **ink**, all three must be the same colour |
| `mesh-vs-fill-rgb.pdf` | *(none)* | the **additive control** — they must match there too |

### ★ Why two mesh types, when one defect caused both

They reach the ink through **different code**, and only one of them is the
shape that actually broke.

- A **type 4** triangle carries its three shades straight into
  `fill_triangle`, which interpolates them barycentrically.
- A **type 6** patch carries four *corner* shades that `Patch::shade_at`
  bilinearly interpolates into a subdivision grid first, via `Shade::lerp`,
  and only then hands triangles to that same rasteriser.

A colorant carrier that survived one path and was dropped by the other would
be invisible to a fixture that tested only one — and the file that exposed
the original defect contains **patches**. Testing only the simpler shape would
have been the more comfortable choice and the wrong one.

### ★★ Why the colour is FLAT, when a mesh's whole purpose is to vary

Because the claim is about colour **transport**, not interpolation. A varying
mesh cannot be compared against a flat fill without choosing a point and then
arguing about whether the chosen pixel is really where you think it is — and
this project has already had one measurement table go wrong exactly that way.
With every vertex the same colour, any pixel of the mesh is comparable to any
pixel of the fill, and a failure means the ink changed on the way.

Interpolation is covered separately, by unit tests in `mesh.rs`, where the
arithmetic is asserted exactly rather than inferred from pixels.

### ★★★ Why the ink is quantised before the fill is written

`BitsPerComponent 8` means the mesh's authored value is
`round(v × 255) / 255`. The flat fill is therefore written with **those**
values — `0.41960784 0.87058824 0.12941176 0.05882353` — and not the nominal
`0.42 0.87 0.13 0.06`.

Otherwise the fixture would carry a built-in 1/255 disagreement, its tolerance
would have to be loosened to accommodate a difference that is nobody's bug,
and a loosened tolerance is how a test quietly stops being able to fail.

The colour itself has all four colorants non-zero and sits nowhere near a
`CMYK ↔ sRGB` fixed point. Pure cyan or black survives the round trip almost
intact and would have let the defect through.

## Verified to fail

Against a build with the mesh branch of `Shading::paint_cmyk` disabled, on
these exact fixtures:

| mark | with the fix | without |
|---|---|---|
| flat fill | `(151, 64, 133)` | `(151, 64, 133)` |
| type 4 mesh | `(151, 64, 133)` | `(160, 90, 113)` |
| type 6 patch | `(151, 64, 133)` | `(160, 90, 113)` |

Mean |diff| `0.00` against `18.33` — the same magnitude the analytic defect
had, because it is the same round trip. `cmyk_bridged_pixels` reports `0`
with the fix and `153,600` without it.

## Regenerating

```
python tools/gen-mesh-ink-fixtures.py
```

The generator is the source of truth; the PDFs are committed so the test suite
does not require Python. Byte-for-byte reproducible — no timestamp, no random
seed, no environment input.
