# icc-rgb — provenance and attribution

Single-page PDF fixtures pinning that **an `ICCBased /N 3` colour is converted
through its own embedded profile on every route** — a fill, a direct sampled
image, an `/Indexed` image, and a JPEG 2000 image whose profile lives in its
codestream — and that the four routes agree with each other. Generated by
`tools/gen-icc-rgb-fixtures.py`; used by `crates/pdfcer-render/tests/icc_rgb.rs`.

The `ICCBased` counterpart of `fixtures/synthetic/devicen-image/`, which pins
the same fill-versus-image agreement for `Separation`/`DeviceN`. Kept as its
own directory for the reason that one states: a different Pass, a different
carrier (an ICC transform rather than a tint function), a different way to fail.

## The files

| file | what it is |
|---|---|
| `swap-rg.icc` | a v2.1 `mntr RGB XYZ` matrix/TRC profile — sRGB's D50-adapted colorants with **red and green swapped**, gamma 2.2 TRCs. Generated by the script. 500 bytes |
| `dest-cmyk.icc` | a two-direction CMYK output profile used as the `/DestOutputProfile` of the third page. **Copied verbatim from iccce** (see below). 10 200 bytes |
| `icc-rgb-four-ways-additive.pdf` | no page group, no output intent — the display route alone |
| `icc-rgb-four-ways-subtractive-no-intent.pdf` | `/Group /CS /DeviceCMYK`, no output intent — the display route feeding the colorant buffer through `rgb_to_cmyk` |
| `icc-rgb-four-ways-subtractive.pdf` | `/Group /CS /DeviceCMYK` and `/OutputIntents` naming `dest-cmyk.icc` — the ink route |

Each page draws the operands `(0.4, 0.2, 0.8)` — exactly `(102, 51, 204)` at
8 bits — four ways in 60 × 60 pt boxes at x = 10, 80, 150, 220 on a
300 × 100 pt page: fill, direct image, `/Indexed` image with one palette
entry, JPX image with no `/ColorSpace` and a `colr` box of METH 2 carrying
`swap-rg.icc`.

## Why the profile swaps red and green

So that the managed and the unmanaged answers are far apart, and so that the
managed answer has a closed form. Because the colorants are exactly sRGB's,
the profile → XYZ → sRGB matrix round trip is the identity (to iccce's 3-ULP
agreement with ICC's published table), and the expected pixel is simply the
sRGB encoding of the swapped gamma-2.2 linear values:

    managed   (48, 102, 205)    = enc(0.2^2.2), enc(0.4^2.2), enc(0.8^2.2)
    unmanaged (102, 51, 204)    = the operands reinterpreted as DeviceRGB

lcms2 (Pillow `ImageCms`, relative colorimetric, 2026-09-02) returns exactly
`(48, 102, 205)` for `(102, 51, 204)` through `swap-rg.icc`, so the closed form
is corroborated by an independent CMM and not only by pdfcer's own. Fifty-four
levels apart in red: a renderer that drops the profile cannot pass by luck
(standing rule R225).

## `dest-cmyk.icc` — attribution

Byte-for-byte `fixtures/synthetic/v2-cmyk-chromatic-neutral.icc` from
**iccce** (`github.com/KenM76/iccce`, MIT, the same author as this project),
at the revision pdfcer pins (`a4d9003bf87c61299fa1c6f9c2e2ffffa30de0c3`).
Generated there by `tools/gen-profiles v2-cmyk-chromatic-neutral`; its
MANIFEST describes it as a v2.4 `prtr CMYK` with Lab PCS, mft2 A2B0 (4→3,
5⁴ grid) and B2A0 (3→4, 9³ grid), both affine. It is used here only as a
destination that turns a colour into all four inks, so the ink probe can
tell a bridged conversion from a `rgb_to_cmyk` reconstruction. Nothing in the
tests depends on its particular numbers.

Rights-cleared per `docs/LEGAL.md` §5: every byte of the PDFs and of
`swap-rg.icc` is generated by the script, and `dest-cmyk.icc` is the
author's own MIT-licensed work from a sibling project.

## Regenerating

    python tools/gen-icc-rgb-fixtures.py

Requires Pillow with OpenJPEG for the JPEG 2000 page. The script asserts that
the JP2 it writes decodes back to the same samples and that the rewritten
`colr` box carries the profile byte for byte, so a half-working fixture cannot
be committed. `dest-cmyk.icc` is read, not written; copy a fresh one from
iccce if it ever needs to change.
