# bilevel — provenance and attribution

Five minimal single-page PDFs exercising the two bilevel image codecs
implemented in Pass 2.2: `CCITTFaxDecode` (ISO 32000-1 §7.4.6, ITU-T
T.4/T.6) and `JBIG2Decode` (§7.4.7, ITU-T T.88). They all draw the
**same 16 × 4 picture**, reached by four different routes, which is what
makes the set useful: a polarity or stride bug shows up as one file
disagreeing with the other four rather than as five files all being
plausibly wrong together.

## Source material and license (LEGAL.md §5)

**Nothing here derives from a third-party file.** This matters more than
usual for these two codecs, because the obvious sources — pdf.js's and
PDFBox's CCITT/JBIG2 regression suites, and the public JBIG2 test
streams — are all third-party files of unknown provenance, which
`docs/LEGAL.md` §5 forbids outright. These are `LEGAL.md` §5 category
(a): **wholly synthetic**, authored for this project, generated by a
committed script from a pixel pattern written by hand.

| Component | Origin |
|---|---|
| The 16 × 4 pixel pattern | Authored for this project; see `INK` in `tools/gen-bilevel-fixtures.py`. |
| The CCITT Group 4 bit stream | Encoded by **libtiff** (via Pillow 12.1.0's TIFF writer, `compression='group4'`) from that pattern, and lifted out of the resulting file's strip. |
| The JBIG2 segment framing | Assembled byte by byte from ITU-T T.88 clause 7's layout. |
| The PDF container | Assembled by the same script: classic §7.5.4 cross-reference table, no object streams, no compression. |

No corpus attribution is required — unlike the sibling `cmyk-variants/`
set, which carries a CC BY 4.0 notice because its JPEG payload came from
the veraPDF corpus.

## Regenerating

```text
python tools/gen-bilevel-fixtures.py
```

The script writes both these PDFs **and**
`crates/pdfcer-core/src/image_codec/fixtures_bilevel.rs`, from the same
bytes, in the same run. That single-source property is deliberate: the
unit tests assert the decoded samples byte-for-byte against
`BILEVEL_16X4_SAMPLES`, and these files are the same payload in a PDF
wrapper, so the two can never drift into disagreeing about what the
picture is.

Requires Pillow with libtiff — a developer-machine dependency only,
never a pdfcer dependency.

## The picture

16 samples wide, 4 rows tall. Each row exercises something different:

| Row | Ink (1 = black) | What it catches |
|---|---|---|
| 0 | `FF 00` | a long black run then a long white run |
| 1 | `00 FF` | the mirror image — a maximal vertical delta for a 2-D coder |
| 2 | `AA 55` | alternating single pixels: T.4's worst case (§7.4.6 NOTE 4's "expansion of 2 : 9") and the row most sensitive to an off-by-one in the run bookkeeping |
| 3 | `C3 C3` | short runs at byte boundaries, where a stride bug shows |

Decoded to PDF samples under the **normal PDF convention** (`0` = black,
which is what `/BlackIs1`'s default of false selects) that is the
complement: `00 FF / FF 00 / 55 AA / 3C 3C`.

Each page is 128 × 128 pt with the image drawn onto a centred 100 pt
square (`100 0 0 100 14 14 cm`), so the margin makes the orientation
obvious at a glance: row 0 must land at the **top**.

## The files

| File | What it pins |
|---|---|
| `ccitt-g4-gray.pdf` | The baseline. `/DeviceGray`, `/BitsPerComponent 1`, `/DecodeParms << /K -1 /Columns 16 /Rows 4 >>`. Renders black-then-white on the top row. |
| `ccitt-g4-blackis1.pdf` | The same bytes with `/BlackIs1 true`. Must render the exact **photographic negative** of the baseline — Table 11's "1 bits shall be interpreted as black pixels … the reverse of the normal PDF convention". A build with the flag wired backwards renders these two files identically-but-swapped, which is the failure this pair exists to make obvious. |
| `ccitt-g4-imagemask.pdf` | `/ImageMask true` with a red non-stroking colour. §8.9.6.2: the samples carry no colour, `/Decode` defaults to `[0 1]` so **0 marks the page**, and that composes with `/BlackIs1` false to put ink exactly where the fax said black. This is the shape most real-world CCITT images take. |
| `jbig2-mmr.pdf` | The same picture as a self-contained JBIG2 stream (T.88 Annex D.3 embedded organization): a page information segment plus an immediate generic region coded with **MMR**, which §6.2.6 defines as T.6 — so the payload is literally the same Group 4 bytes. Must render **pixel-identical** to `ccitt-g4-gray.pdf`, despite T.88 fixing black at bitmap value 1 and PDF's convention being the opposite. |
| `jbig2-mmr-globals.pdf` | The same JBIG2 stream **split in two**: the page information segment lives in a separate stream object referenced by `/DecodeParms << /JBIG2Globals 6 0 R >>` (Table 12), and only the region segment is the image's own data. Neither half decodes alone. This is the only file in the set that exercises the reference → stream → span → filter-chain resolution that `/JBIG2Globals` requires, and which is one of the two mechanical reasons the codec layer takes a `&Document` at all (decision 005 §1.2). |

## Uses

1. **Seed corpus** for the whole-file fuzz targets (`load_document`,
   `parse_object`) — decision 005 §6.5 requires fuzz seeds to come from
   `fixtures/synthetic/` and never from a downloaded real-world PDF.

   Note the codec targets want something narrower: `image_codec_ccitt`
   and `image_codec_jbig2` consume an `arbitrary`-derived parameter
   struct whose *tail* is the raw codestream, so their most productive
   seeds are the bare `CCITT_G4_16X4` / `JBIG2_MMR_16X4` byte arrays
   from `crates/pdfcer-core/src/image_codec/fixtures_bilevel.rs`
   (identical bytes, same generator run) rather than these PDF
   wrappers.
2. **End-to-end demo / smoke test** — the byte arrays in
   `fixtures_bilevel.rs` prove the codec adapters; only a real file
   proves the whole path from xref parsing through the content stream to
   the rasterizer:

   ```text
   pdfcer render-page fixtures/synthetic/bilevel/ccitt-g4-gray.pdf \
       --page 1 --scale 3 --output out.png
   ```

   Every one of the five must report `images=1 images_unsupported=0
   images_codec_unsupported=0 codec_features=0
   codec_geometry_mismatch=0`.
