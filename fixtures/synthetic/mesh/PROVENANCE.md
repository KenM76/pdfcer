# mesh — provenance and attribution

Single-page PDF fixtures for **mesh shadings** — `ShadingType` 4, 5, 6 and 7
(ISO 32000-1 §8.7.4.5.5–.8), the four types whose geometry lives in a stream
rather than in a dictionary. Rendered by
`crates/pdfcer-render/src/mesh.rs`; used by
`crates/pdfcer-render/tests/mesh_shadings.rs`.

Sibling of `fixtures/synthetic/transparency/`, and built for the same reason
that directory gives: unit tests prove an evaluator's arithmetic, and only a
real PDF proves the arithmetic is wired to a content stream.

## Source material and license (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** These are `LEGAL.md` §5
category (a): **wholly synthetic**, authored for this project, generated by a
committed script (`tools/gen-mesh-fixtures.py`) from geometry and colours
this project chose — a square, its four corners, four saturated primaries.
No attribution is owed or claimed, and nothing was downloaded from anywhere.

★ **This point is load-bearing rather than boilerplate here.** The only mesh
shadings this project has real-world access to live inside a **licensed**
print-conformance patch, which `docs/LEGAL.md` §5 forbids checking in and
which the 2026-08-25 operator ruling forbids even naming in this repository.
The type 7 fixtures below are built from **the standard's own equations**
— §8.7.4.5.8's four `1/9 (…)` internal-point formulas, transcribed
independently in the generator — not from any sample, any capture, or any
paraphrase of one.

The PDFs are assembled **byte by byte** from a classic §7.5.4 cross-reference
table with no object streams and no compression, so a failing test can be
diagnosed in a hex editor and a fuzzer mutating one keeps producing something
a parser will engage with.

## What each file is for

Every file is 120 pt square, and every mesh covers `[10, 110]²` in page
coordinates, so a test can name a corner in the units the generator used.

| file | what it is | what only it can catch |
|---|---|---|
| `type4_triangles.pdf` | two triangles, edge flags `0, 0, 0, 1` | the flag state machine's relabelling (`MSH19`) |
| `type5_lattice.pdf` | a 2×2 lattice, **no flag field at all** | a parser that leaves `BitsPerFlag` in a type 5 record (`MSH7`), and the vertex padding rule at the width where it bites |
| `type6_coons.pdf` | one Coons patch, 12 control points | the boundary-curve order and the corner-colour walk (`MSH25`, `MSH24`) |
| `type7_tensor.pdf` | the same patch as 16 **explicit** points | the internal-point cycle `p11 p12 p22 p21`, which is not row-major (`MSH29`) |
| `type6_flag1.pdf` | two patches, the second continuing on edge 1 | the inheritance table's flag-1 row — the new `u = 0` edge is the previous patch's `v = 1` row, **not** reversed |
| `type6_flag2.pdf` | the same, on edge 2 | flag 2 inherits the previous patch's `u = 1` column **reversed** |
| `type6_flag3.pdf` | the same, on edge 3 | flag 3 inherits the previous patch's `v = 0` row **reversed** |
| `type7_flag1.pdf` | a continued **type 7** patch | that a continued type 7 record is **12** coordinate pairs, not 8 — the four internal points are never inherited |
| `type4_parametric.pdf` | type 4 with a **non-linear** `/Function` | `f(lerp(t))` versus `lerp(f(t))` (`MSH14` clause 3) |
| `type6_unaligned.pdf` | `BitsPerFlag 4`, `BitsPerCoordinate 12`, `BitsPerComponent 4` | the `MSH-A1` patch-padding ambiguity, which is **unobservable on any byte-aligned file** |
| `type4_truncated.pdf` | a stream cut part-way through its fourth vertex | that complete records still paint and the tail is disclosed (`MSH-N2`) |
| `type4_indexed.pdf` | an `Indexed` colour space | the `MSH-A4` refusal — a literal reading would interpolate palette **indices** |
| `type6_pattern.pdf` | the same Coons patch reached as a `PatternType 2` **fill** | the other paint route. `sh` and a shading pattern anchor in opposite coordinate spaces, and a mesh **inverts** the transform the analytic path uses directly |

## The two equivalence pairs, and why they are the point

A rendered gradient has no obviously-right answer, and a committed
"known good" PNG only pins whatever the code did the day it was taken. So
the strongest assertions in the test file are **agreements the standard
requires between two files that reach the same picture by different code
paths**:

- `type6_coons.pdf` ≡ `type7_tensor.pdf` — a Coons patch *is* a tensor patch
  whose four internal points its boundary implies (`MSH30`). The type 7 file
  carries those points explicitly, computed by the generator's own
  transcription of the equations; `mesh.rs` derives them from the boundary.
  Two independent transcriptions meeting at the same picture is stronger than
  either matching a stored image.
- `type4_triangles.pdf` ≡ `type5_lattice.pdf` — the flag sequence `0,0,0,1`
  builds exactly the two triangles a 2×2 lattice builds, across two parsers
  with different record shapes.

`type6_coons.pdf` and `type4_triangles.pdf` must **differ**, and the test
file asserts that too: it is what keeps the two agreements above from being
two renders of nothing.

## How to regenerate

```
python tools/gen-mesh-fixtures.py
```

The script is the authority; these files are its output and are checked in
only so that `cargo test` needs no Python.
