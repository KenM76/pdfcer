# addtext — provenance and attribution

Three minimal PDFs, generated byte by byte by
`tools/gen-addtext-fixtures.py`, for **Pass 16.0** (add NEW page text as real
page content — decision 016 / FF-D — `pdfcer_core::text_edit::addtext`):

- `plain.pdf` — one page, a single `/Contents` stream, the page's OWN
  `/Resources` (`/Font << /F1 … >>`). Content: one run "Original page text".
  Proves: adding text leaves the original content stream **byte-identical**
  (the incremental output's prefix is the input); the new run renders (R59)
  and re-extracts; a `/Font` entry merges into the page's own resources. Also
  the missing-glyph refusal case (add a non-WinAnsi character → refused).
- `inherited-resources.pdf` — TWO sibling pages (objects 3, 4) that both OMIT
  `/Resources` and INHERIT the `/Pages` node's (object 2) `/Resources`
  (`/Font << /F1 5 0 R >>`). Proves the §7.7.3.4 inheritance trap: adding text
  to page 0 gives that page its OWN `/Resources` (referencing the same `/F1`)
  plus the new font, and does **not** re-emit / mutate the shared object 2 —
  sibling page 1 is untouched.
- `tagged.pdf` — one page whose run sits inside `/P << /MCID 0 >> BDC … EMC`,
  with the catalog carrying `/MarkInfo << /Marked true >>` and a minimal
  `/StructTreeRoot`. Proves R73: a new run added to a tagged page is emitted as
  **untagged** page content and that fact is disclosed (no structure element is
  fabricated).
- `certified-locked.pdf` — `plain.pdf` PLUS an **enforced certification**
  (DocMDP) signature: the catalog carries `/Perms << /DocMDP 6 0 R >>` and
  object 6 is a signature dictionary (`/Type /Sig`, `/ByteRange`) whose
  `/Reference` is a `/DocMDP` transform with `/TransformParams << /P 1 >>`
  (ISO 32000-1 §12.8.4 Table 258 / Table 254 P=1 — "no changes permitted").
  Proves the **add-text certification guard** (FF-D follow-up): because
  `/Perms → /DocMDP` is present, enforcement is a `shall`, so adding page
  content — point OR box — is **refused** with the same
  `CertificationForbidsChange` refusal `EditSession::add_markup` raises, rather
  than silently invalidating the signature. The `/ByteRange` / `/Reference`
  values are structural placeholders (no real signed bytes); only the
  census-visible structure matters to the guard.

## Source material and license (LEGAL.md §5)

**No structural byte here derives from a third-party PDF.** Every file's object
layout, cross-reference table, page tree and content stream is authored in the
committed generator (`tools/gen-addtext-fixtures.py`), with no PDF library
behind it (same discipline as the sibling `tools/gen-*-fixtures.py`). Classic
cross-reference table, exactly-20-byte entries (ISO 32000-1 §7.5.4), no `/ID`,
no timestamps ⇒ running the generator twice produces byte-identical files.

The visible text is placeholder English ("Original page text", "Page one
inherited", "Tagged run") carrying no expressive content — LEGAL.md §5 category
(a), **wholly synthetic**, CC0-equivalent.

### Fonts — NO embedded program, no third-party bytes

Every font in these fixtures is a **non-embedded named Standard-14 simple
font** (`/Type /Font /Subtype /Type1 /BaseFont /Helvetica /Encoding
/WinAnsiEncoding`) with **no `/FontFile`**. Pass 16.0 never embeds a glyph
program (R79), so — unlike the `textedit` corpus, which embeds a bundled Foxit
Base-14 face to exercise the embedded/subset edit cases — these fixtures
introduce **no font program bytes at all**. The renderer supplies the std-14
outlines from its own bundled faces at display time (disclosed as `Bundled`
substitutes, decision 004 §4.2).

## Regenerating

```
python tools/gen-addtext-fixtures.py
```

The output is committed. Re-run after changing the generator.
