# forms — provenance and attribution

Synthetic AcroForm fixtures for Pass 7 (interactive forms / form fill;
ISO 32000-1 §12.7, `docs/decisions/008`). `demo-form.pdf` is a single
300×200-unit page carrying an `/AcroForm` with two terminal fields —
a merged (Shape A) text field `FullName` (`/FT /Tx`, no `/AP` until
filled) and a merged check box `Subscribe` (`/FT /Btn`, `/AP /N`
subdictionary keyed `/Yes` and `/Off`) — plus the AcroForm `/DR /Font`
`/Helv → Helvetica` a `/DA` resolves against. It exercises the fill
path end to end: `fill-field` sets the text value + regenerates its
`/AP` (§12.7.3.3) and checks the box (state selection, §12.7.4.2.3).

## Source material and license (LEGAL.md §5)

**Nothing here derives from a third-party file.** These are `LEGAL.md`
§5 category (a): **wholly synthetic**, authored for this project and
generated byte by byte by a committed script (`tools/gen-form-fixtures.py`)
with no PDF library behind it — so a fixture cannot inherit a bug (or a
normalization) from the code it tests, and no attribution is owed or
claimed. Each file is a single page with a classic §7.5.4 cross-reference
table and no encryption, no object streams, and no embedded font
programs (the standard-14 `/DR` font is the bare §9.6.2.1 four-key form).

## `radio-choice-form.pdf` (added 2026-08-06)

Generated by `tools/gen-form-radio-choice-fixture.py`, same category (a)
terms as the file above: **wholly synthetic**, byte-authored by a committed
script, no third-party source, no attribution owed or claimed.

Four fields on one 300x260 page, each present because the Forms panel's
radio/choice support could not otherwise be tested at all:

| Field | Shape | What it exists to catch |
|---|---|---|
| `Colour` | `/Btn` `/Ff 32768` (`Radio`), three widget kids with on-states `/Red` `/Green` `/Blue`, `/V /Green` | Reading an EXISTING selection, and exclusivity when a new one is set |
| `Locked` | `/Btn` `/Ff 49152` (`Radio` + `NoToggleToOff`) | That a "Clear" affordance is NOT offered where the engine would refuse it — the rule is unfalsifiable without a field that sets the flag |
| `Country` | `/Ch` `/Ff 131072` (`Combo`), `/Opt` of `[export display]` PAIRS, `/V (MX)` | **Export vs display.** With the two equal, a panel that shows the wrong one is invisible; here it shows `MX` instead of `Mexico`. It caught exactly that defect on first run. |
| `Toppings` | `/Ch` `/Ff 2097152` (`MultiSelect`), bare-string `/Opt`, `/V [(Olives)]` | The OTHER `/Opt` form, and multi-selection |

`/Opt` order is deliberately non-alphabetical (`Canada`, `Mexico`,
`Argentina`) because §12.7.4.4 makes displaying `/Opt` order a reader
**shall**; an alphabetical fixture would let a sorting bug pass unnoticed.

Every field carries `/Kids` down to its widget(s) as well as the widget's
`/Parent` back up. The first draft omitted `/Kids` on the two `/Ch` fields
and pdfcer correctly reported `widgets=0` for them — a fixture defect, not a
parser defect, and worth recording so the next author does not repeat it.

## The five field-hierarchy fixtures (added 2026-08-07)

Generated by `tools/gen-form-hierarchy-fixtures.py`, same category (a) terms
as every file above: **wholly synthetic**, byte-authored by a committed
script with no PDF library behind it, no third-party source, no attribution
owed or claimed. Each uses a classic §7.5.4 cross-reference table, no
encryption, no object streams, and the bare §9.6.2.1 four-key standard-14
font form — so a defect in any of those layers cannot masquerade as a
field-tree defect.

They exist because `ROADMAP.md`'s Pass 7.0 entry records that the organic
corpus **contains no nested field trees at all** (max 63 fields/file, 1x on
depth, zero nesting). Every non-terminal path in `forms::walk_field` had
therefore never run against real data. That was survivable while pdfcer only
read forms; field authoring ends it, because authoring exists to GENERATE
those shapes.

| File | Shape | What it exists to catch |
|---|---|---|
| `multi-widget-form.pdf` | One terminal `Reference`, **3 kid widgets across 2 pages** | Fan-out. Three widgets rather than two defeats an off-by-one; two pages rather than one defeats a flatten that burns everything onto page 1 |
| `nested-form.pdf` | 2-level hierarchy → `Personal.Address.Zip` | FQN composition across two levels, and inheritance of `/FT` from a grandparent + `/DA` from a parent. `Personal.Name` sits one level shallower on purpose, so a walk with a single shared depth counter gets one of the two wrong |
| `radio-group-form.pdf` | `/Btn` `Radio`, 3 kids, on-states `/Red` `/Green` `/Blue` | Core-side exclusivity over a `/Kids` group (distinct from `radio-choice-form.pdf`, which serves the GUI panel). Each kid's `/AP /N` has **two** keys — a group with no `/Off` stream cannot deselect |
| `mixed-kids-form.pdf` | `Order`: `/FT`, `/V`, **and** `/Kids [widget, Qty]` | **The one that was broken.** See below |
| `xfa-hybrid-form.pdf` | AcroForm + a 2-packet `/XFA` array | That creation refuses (§3.2.2) while reading and filling still work |

On-state names are `/Red` `/Green` `/Blue` rather than the positional `/1`
`/2` `/3`: positional names are legal (Table 227) but pdfcer cannot resolve
them to export values, so a positional fixture would test a shape pdfcer has
explicitly not committed to.

### What `mixed-kids-form.pdf` caught, measured

§12.7.3.1's merge rule classifies each `/Kids` entry **individually** — a kid
with its own `/T` is a child field, a `/T`-less widget kid is one of the
parent's own appearances. Nothing in the spec says a node must pick one KIND
of kid.

`walk_field` did pick one. It partitioned `/Kids`, and if any kid was a field
it recursed into those and **returned** — so a mixed node's own widgets were
never modelled and the node never reached the projection. Before the fix:

```
$ pdfcer list-fields fixtures/synthetic/forms/mixed-kids-form.pdf
field name=Order.Qty ... value=3 widgets=1
... fields=1
```

`Order` — carrying `/V (ORD-77)` and a widget the page's `/Annots` still
referenced — was absent from `list-fields`, from `regenerate-appearances`
(`regenerated=1`), and would have been absent from `export-data` and
`flatten`. A viewer painted a field the form did not contain. After:
`fields=2`, `regenerated=2`.

The merge primitive can generate this shape by attaching a widget to a node
that already has a child field, which is why the fixture is part of the
authoring substrate rather than a curiosity.

## `js-carriers-form.pdf` and `tagged-struct-tabs.pdf` (added 2026-08-07, both generated by the same `tools/gen-form-hierarchy-fixtures.py` as the five above)

Same category (a) terms as every fixture in this file: **wholly
synthetic**, byte-authored by the committed script, no PDF library behind
either one, no third-party source, no attribution owed or claimed. Both
were generated alongside the five field-hierarchy fixtures above but this
entry was not written until the filing that documents the two commits
that actually exercise them.

**`js-carriers-form.pdf`** exists for decision 020 §7.2's byte-grep test.
Pass 7.0 guarantees that the three JavaScript carriers pdfcer recognizes
but never executes (decision 009) — `/AcroForm /CO`, a field `/AA`, and
the document-level `/Names /JavaScript` tree — re-emit BYTE VERBATIM.
That guarantee held *structurally* before field authoring existed: filling
a field never writes `/AcroForm` at all, so nothing could disturb `/CO`.
Field *creation* must write `/AcroForm /Fields`, which means the guarantee
stops being structural the moment authoring ships, and because it had
never been asserted, no existing test would go red when it broke. The
fixture places each carrier where an authoring write actually passes
close to it: `/CO` in the `/AcroForm` dict field registration rewrites,
`/AA` (`/C` calculate hook + `/F` format hook) on a field beside the
`/Fields` array that grows, and `/Names /JavaScript` in the CATALOG — the
object the `/AcroForm`-absent creation path writes when there was no form
at all. The JavaScript content itself is inert and deliberately trivial;
pdfcer must never parse it, so the content buys no coverage — only the
BYTES are the test. Exercised by
`authoring_a_field_leaves_the_javascript_carriers_intact`.

**`tagged-struct-tabs.pdf`** exists for the two decision-020 accessibility
disclosures shipped 2026-08-07 (`50a5461`). It carries a minimal but
well-formed `/StructTreeRoot << /K [] >>` (so `/MarkInfo /Marked true` and
tag-tree presence are genuinely true, not merely claimed) and a page that
declares `/Tabs /S` directly rather than inheriting it from the page tree
— the shape a real producer writes, and the base case the inheriting
`/Tabs` lookup has to get right before ancestor-walking matters at all.
Two disclosures are unreachable without it, and neither is a restatement
of the other: **(1)** the document is tagged and a pdfcer-authored field
cannot be, because pdfcer has no structure-tree writer (§3.5.3 — a partial
tag-tree writer was rejected in favour of disclosing the gap); **(2)** the
page's tab order is *computed from the tag tree* under `/Tabs /S`
(§14.7, Table 30), so an untagged field on this specific page has **no
tab position at all** — undefined, not "last" — which is a functional
defect in the form and not only an accessibility gap (§3.4.3). Without
this fixture both disclosures would be correct, wired, and never fire —
exactly the shape R96 exists to forbid. The structure tree is deliberately
no fuller than an empty `/K []`: pdfcer's own check reads no further than
"is `/StructTreeRoot` present", so a richer tree would add bytes without
adding coverage.

### A second defect these fixtures surfaced, in a file that predates them

Running flatten over `demo-form.pdf` — the shipped Pass 7 fixture, unchanged
— showed `/AcroForm /Fields [4 0 R 5 0 R]` surviving in the saved bytes while
objects 4 and 5 were deleted. `acroform_id` returns the object that *holds*
the form, which for a direct `/AcroForm` is the **catalog**, one level above
the dict `/Fields` lives in; the removal path read `/Fields` off the catalog,
found nothing, and its guard never fired.

Every forms test asserted through `parse_acroform`, which resolves each
`/Fields` entry and drops the unresolvable ones — so the projection reported
an empty form while the file named deleted objects. The regression test for
it (`flatten_clears_the_fields_array_in_the_saved_bytes`) therefore asserts
on **bytes**, not on the model.

## `certified-p2-form.pdf` — the certification level that SEPARATES two gates

Byte-authored by `tools/gen-form-certified-p2-fixture.py`; no PDF library
is involved, so it cannot inherit a bug from the code it tests.

`demo-form.pdf`'s two merged fields (`FullName` text, `Subscribe` check
box) plus `/Perms << /DocMDP >>` on the catalog and a signature dictionary
whose `/DocMDP` transform carries **`/P 2`** — "filling in forms and
signing is permitted" (§12.8.4 Table 254).

**Why a new fixture rather than reusing `addtext/certified-locked.pdf`.**
That file is `/P 1`, "no changes permitted", and refuses *everything*.
`EditSession::fill_refusal` and `EditSession::deletion_refusal`
deliberately use different gates — filling takes the `/P`-aware one,
deletion takes the strict one — so a test written against `/P 1` passes
whether or not those gates differ at all, and would keep passing if
someone collapsed one into the other. **R162**: an assertion that cannot
come out false.

`/P 2` is the only value where the two disagree, and it is not an exotic
one — a certified fillable form is the ordinary real-world case. It is
what makes "pdfcer offers filling and refuses deletion on the same
document" a testable claim rather than a doc comment.

The `/ByteRange` and `/Reference` are structural placeholders with no
signed bytes, deliberately: the guards read census-visible *structure* and
verify no cryptography, so real signing would test a claim pdfcer does not
make while adding a key nobody can rotate.

Two fields rather than one because deleting a text field and deleting a
button travel slightly different paths in the panel, and a one-field
fixture would let a regression in either hide.

## `unfillable-fields-form.pdf` — rows that cannot be FILLED but can be DELETED

Byte-authored by `tools/gen-form-undeletable-looking-fixture.py`.

Four merged fields: `Locked` (text, `/Ff 1` read-only), `Approved`
(`/FT /Sig`, unsigned), `Submit` (`/FT /Btn` `/Ff 65536`, push button),
and `Notes` — an ordinary fillable field kept as a control.

**The distinction it exists to pin down.** `deletion_preflight` checks
encryption and certification and *nothing else* — no read-only test, no
field-type test — so all three unfillable shapes are perfectly
deletable. The forms panel used to `continue` past such rows after
printing why they could not be filled, which also skipped the delete
control and withheld an affordance the capability actually had. R83
forbids offering what you cannot do; it does not license withholding
what you can.

Without a fixture carrying such a field the fix is invisible: every
forms fixture before this one had only fillable fields, so a test would
have had nothing to assert on and the regression could return
unnoticed. **R162** — the container has to be shown capable of holding
the thing.

The control field is not decoration. If the panel ever stops rendering
controls for *all* rows, `Notes` fails too and the fixture reports a
blanket regression rather than letting it read as the fix working.

All four are Shape A (merged field/widget), so each shows a single
"Delete field" control — this fixture is about *which rows get a
control*, not the single-vs-multi split, which `radio-group-form.pdf`
covers.

## `rich-field-form.pdf` and `rival-font-form.pdf` (added 2026-08-29)

Generated by `tools/gen-form-clipboard-fixtures.py`, same category (a) terms
as every file above: **wholly synthetic**, byte-authored by a committed
script, no third-party source, no attribution owed or claimed.

Both exist for `Pass 167.0` (the field clipboard — `copy_field` /
`paste_field`), and the reason they had to be new files rather than a reuse of
`demo-form.pdf` is the whole point of the pair:

**Field CREATION chooses every value itself, so a fixture carrying the
authoring defaults can verify it. A field COPY is judged entirely on values
pdfcer did NOT choose — and every one of them is invisible when the fixture's
value happens to equal the default.** A `/DA` of `/Helv 0 Tf 0 g` cannot show
that font, size and colour travelled; it is exactly what a re-author would
have written anyway. A black `/MK /BC` cannot show that the border colour
travelled; `add_text_field` hard-writes black. A `/DA` naming `/Helv` cannot
show that the `/DR` font travelled; `ensure_default_resources` puts `/Helv` in
every destination regardless. Tests written against a default-valued fixture
would have passed against an implementation that carried nothing at all.

### `rich-field-form.pdf`

One 400×300 page, one merged (Shape A) text field `TitleBlock.Revision` under
a grouping node `TitleBlock` — dotted, so the paste's path splitting is
exercised too. Nothing on it is at its default:

| key | value | what it catches |
|---|---|---|
| `/DA` | `/TB 14 Tf 0 0 1 rg` | font, size and colour, none of them the default; and a font resource name that is **not** `/Helv` |
| `/DR /Font /TB` | Helvetica-Bold | the carried font: a destination lacking `/TB` must gain it, or the `/DA` does not resolve (§12.7.3.3) |
| `/Q` | 1 (centred) | quadding |
| `/MaxLen` | 12 | the length limit |
| `/DV` `/V` | `(A)` / `(C)` | deliberately **different**, so "the default value travels while the value does not" is falsifiable |
| `/TU` | `(Revision letter)` | the accessibility name, and R105's `Carry` answer |
| `/Ff` | 4194304 | `DoNotSpellCheck` (bit 23) — a flag **no `New*Field` spec can express**, so it can only arrive by being carried |
| `/MK /BC` `/BG` | blue / cream | the reported "a blue-bordered field pastes black"; nothing in pdfcer authors a `/BG` at all |
| `/BS` | `/S /D /W 2` | dashed, 2 pt — neither of them the default |
| `/AP /N` | a real stream with its own `/Resources` | the baked appearance and its closure |
| `/AA /C` + `/AA /F` | JavaScript streams | the calculate action, which obliges `/AcroForm /CO` (Table 218) |
| `/AcroForm /CO` | one entry | so "`/CO` grew by exactly one" is measurable against a source that already had one |

**pdfcer never executes the JavaScript** (decision 008 §5.1, NF4) — it is here
so the clipboard's carry-or-drop decision has something real to carry or drop.

### `rival-font-form.pdf`

One 400×300 page, an `/AcroForm` with no fields, and a `/DR /Font /TB` that is
**Courier** — deliberately a *different* font from the rich fixture's `/TB`.

It exists for exactly one test: pasting the rich field here must not overwrite
the destination's own `/TB`, must install the carried font under a free name
(`/TB_1`), and must rewrite the pasted field's `/DA` to name it. Without a
fixture whose `/TB` **disagrees**, a paste that silently clobbered the
destination's font would have passed.
