# devicen-image — provenance and attribution

Single-page PDF fixtures pinning that **a `Separation`/`DeviceN` image and a
flat fill of the same authored tint render the same colour** on a page that
composites in ink, plus two image-only pages pinning that **an image's own
colour conversions are reported at all**. Generated by
`tools/gen-devicen-image-fixtures.py`; used by
`crates/pdfcer-render/tests/devicen_image_ink.rs`.

The image counterpart of `fixtures/synthetic/shading/` (analytic shadings) and
`fixtures/synthetic/mesh-ink/` (meshes), which pin the same property for the
other two object types. The three directories are deliberately separate for
the reason `mesh-ink/` states: they were fixed in different Passes, they fail
for different reasons, and one directory would hide that each object type
needed a different carrier for its colorants.

## The six files

| file | what it is for |
|---|---|
| `separation-image-vs-fill-cmyk.pdf` | `/Separation /SpotGreen /DeviceCMYK`, subtractive page — the direct, spot-only route |
| `devicen-image-vs-fill-cmyk.pdf` | `/DeviceN [/Cyan /Magenta] /DeviceCMYK`, subtractive — the route where the authored tints and the transform's output **differ** |
| `duotone-image-vs-fill-cmyk.pdf` | `/Indexed` over that `/Separation` — the palette route |
| `separation-image-vs-fill-rgb.pdf` | the same `/Separation`, **no page group** — the additive control |
| `image-only-good-tint.pdf` | one image and nothing else, working `/tintTransform` |
| `image-only-broken-tint.pdf` | the same with a deliberately malformed one |
| `duotone2-image-vs-fill-cmyk.pdf` | `/Indexed` over `/DeviceN [/Black /SpotGreen]` — the MIXED duotone (`Pass 238.0`); found two `/Indexed` operand bugs on the fill route |
| `stencil-spot-vs-fill-cmyk.pdf` | an `/ImageMask` stencil filled in the `/Separation` beside a path fill of the same tint (`Pass 238.0`) |
| `duotone2-op-image-over-cmyk-mark.pdf` | a `1 0 1 .5 k` mark, then the mixed duotone image over it under `/OP true` (`Pass 238.0`) — the suite's duotone-patch shape |

★ The last two carry **no fill**, and that is the measurement rather than a
simplification. A fill's colour conversions are counted, so on any page that
has one the counter reads a plausible non-zero number whether or not the image
contributes — **a page with a second producer cannot detect a missing
producer**. That is how an image's diagnostics went unreported for as long as
they did.

★ The `/DeviceN` page's tint transform is deliberately **not** a pass-through:
it maps `(t0, t1)` to `(0.9·t0, 0.8·t1, 0.1, 0.05)`. A fixture whose transform
is the identity cannot distinguish "which components did the source *specify*"
(§11.7.4.3 Table 149's question) from "what does the transform *produce* in the
alternate space", and telling those apart is the whole content of the Pass
these were built for.

## Source material and license (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** These are `LEGAL.md` §5
category (a): **wholly synthetic**, assembled byte by byte from ISO 32000-1's
own object syntax by a committed script — §8.6.6.4 for `/Separation`, §8.6.6.5
for `/DeviceN`, §8.6.6.3 for `/Indexed`, §7.10.2 and §7.10.4 for the type 2 and
type 4 tint transforms, §8.9 for the image XObjects. No attribution is owed or
claimed, and nothing was downloaded from anywhere.

**★ In particular, no byte and no structure of the licensed print-conformance
suite is reproduced.** That suite is where the operator's defect was measured,
and it is not redistributable, not in this repository, and not present on a
fresh clone or on CI. These files are deliberately not a reconstruction of it:
different colorant names, different page size, a 200×200 pt page against that
suite's 90×50 mm, no reference image, no caption, no trap mark, a **flat**
colour where that suite uses a photograph, and a two-colorant `/DeviceN` where
the patch that prompted the work uses five.

Every stream is stored **uncompressed** and the cross-reference section is a
classic **table**, not a stream. Both are deliberate: these fixtures test
colour, and a reader debugging one should be able to read its bytes without
decompressing anything first.

## Regenerating

```
python tools/gen-devicen-image-fixtures.py
```

Deterministic — no timestamps, no random data, no `/ID`. Re-running it on an
unchanged script reproduces byte-identical files, so a diff in this directory
always means the generator changed.

★ The generator asserts its object numbers are **contiguous from 1** before
serialising. A classic cross-reference table is written as one contiguous
subsection, so a gap silently shifts every entry after it and the file dies
with a message naming the symptom (`object at xref offset N declares X, xref
expected Y`) rather than the cause. That assertion exists because it happened
while these files were being written.
