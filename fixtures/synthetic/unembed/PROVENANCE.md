# `fixtures/synthetic/unembed/` — provenance

**Generator:** `tools/gen-unembed-fixtures.py`. Run it from the repo root:

```
python tools/gen-unembed-fixtures.py
```

Every file in this directory is reproducible from a clean checkout with that
one command and no arguments — the lesson `gen-encryption-fixtures.py`'s own
header records at length (a fixture whose construction nobody can repeat is a
fixture nobody can extend).

**Rights (project rule 7, `docs/LEGAL.md` §5):** every byte is synthetic and
self-authored. No real-world PDF of unknown provenance is present or was
consulted. The embedded font programs are the project's own
`fixtures/synthetic/text/subset-fstype-*.ttf` donors, themselves generated by
`tools/gen-subset-font-fixtures.py`.

**Consumed by:** `pdfcer_core::font_unembed`'s unit tests, and `pdfcer`'s
`unembed-font` integration tests.

## Why this directory exists alongside `fontinfo/`

`fontinfo/` covers the **classifier** — one file per removability verdict.
This directory covers what a classifier cannot reach: the **structural**
hazards that only matter once pdfcer starts deleting objects, and the
disclosures that only matter once it does. Two font dictionaries sharing one
descriptor is not a classification question; it is a question about whether
an edit to one object silently changes another font.

## What each file pins

| File | Branch under test |
|---|---|
| `unembed-shared-program.pdf` | ★ Two descriptors, **one** `/FontFile2` object. The removable font unembeds; the stream is **not freed**, because a blocked font still reaches it. Deleting it would blank the font pdfcer explicitly refused to touch — the failure this fixture exists to make impossible. |
| `unembed-shared-descriptor.pdf` | ★ Two font dictionaries, **one** `/FontDescriptor` object. The removable font is **blocked outright** (`descriptor-shared`): editing that descriptor would unembed a font whose verdict said no. |
| `unembed-many-pages.pdf` | One font object reached from five pages. Deduplicated to ONE target listing five pages, and one deletion — a per-page loop would delete the same object five times and count its bytes five times. |
| `unembed-acroform-dr.pdf` | A removable embedded font reachable **only** from the AcroForm `/DR /Font` (§12.7.2 Table 218). Its `pages` list is empty, so an implementation that keyed deletion off pages would find nothing to do while reporting a font it could remove. |
| `unembed-charset-cidset.pdf` | A descriptor carrying BOTH `/CharSet` (Table 122) and `/CIDSet` (Table 124). Both go with the program, the `/CIDSet` **stream** is freed, and everything §9.8.1 names as substitution input stays. |
| `unembed-direct-fontdict.pdf` | The font dictionary written INLINE in the page's `/Resources` (§7.3.7 permits it). No object identity, so it is blocked by name (`font-not-indirect`) rather than silently skipped. |
| `unembed-inline-descriptor.pdf` | The `/FontDescriptor` written INLINE in an **indirect** font dictionary. Addressable — writing the font dictionary writes it — so it unembeds. The pair with the row above is what proves the two "direct" cases are not being confused: one has an object to write, the other does not. |
| `unembed-pdfa.pdf` | XMP `pdfaid:part` / `pdfaid:conformance` in the catalog `/Metadata`, plus a `GTS_PDFA1` output intent. Unembedding breaks the conformance the file claims, and the plan must say so before anything happens. |
| `unembed-shortest-subset-tag.pdf` | `/BaseFont /ABCDEF+X` — the shortest name §9.6.4 can tag. See below. |

## ★ Why `/CIDSet` appears on a simple font, deliberately

Table 124 puts `/CIDSet` on a **CIDFont** descriptor, and phase A's classifier
never returns `Removable` for a composite font — so a *conforming* document
cannot present the combination "removable font whose descriptor carries
`/CIDSet`". The handling exists anyway, because a descriptor carrying the
entry is asserting *"this used to be a subset"*, which is exactly the false
claim unembedding must not leave behind. Code that no test can reach is code
nobody has checked, so `unembed-charset-cidset.pdf` is malformed on purpose
and says so here rather than letting the branch go untested because the legal
shape does not exist.

## ★ A guard that turned out to be unreachable, found by building a fixture for it

`font_unembed::rename_for` declines to strip a subset tag when the family part
would be empty — the `ABCDEF+` case. This directory's ninth fixture was
written to reach that branch. **It does not, and cannot.**

`fontinfo::split_subset_tag` requires `len() > 7` before it will call anything
a §9.6.4 tag, so a bare `ABCDEF+` (exactly seven bytes) carries **no tag at
all** and the whole string stays the name. The shortest string the splitter
will actually split is `ABCDEF+X`, which leaves one character behind. The
empty-family guard was written for a case the splitter forbids.

The guard stays — an empty `/BaseFont` is the one output worse than a tagged
one, and the invariant it depends on lives in a different function — and the
fixture was renamed for what it really pins: the boundary case where stripping
leaves a one-character family name. That is the finding, and it was produced
by trying to make a branch fail rather than by reading the code.
