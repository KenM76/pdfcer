# `fixtures/synthetic/embed/` — provenance

**Generator:** `tools/gen-embed-fixtures.py`. Run it from the repo root:

```
python tools/gen-embed-fixtures.py
```

Every file in this directory is reproducible from a clean checkout with that
one command and no arguments — the same discipline the sibling `unembed/` and
`encryption/` fixture sets hold themselves to (a fixture whose construction
nobody can repeat is a fixture nobody can extend).

**Rights (project rule 7, `docs/LEGAL.md` §5):** every byte is synthetic and
self-authored. No real-world PDF of unknown provenance is present or was
consulted. The **donor** font programs used by the tests over these files are
the project's own `fixtures/synthetic/text/subset-fstype-*.ttf` faces,
generated by `tools/gen-subset-font-fixtures.py`.

**Consumed by:** `pdfcer_core::font_embed_missing`'s unit tests,
`pdfcer_core::edit`'s embed tests, and `pdfcer`'s `embed-font` tests.

| File | Branch |
|---|---|

| `embed-std14-encoded.pdf` | The same, but with `/Encoding /WinAnsiEncoding` already present. pdfcer must not write an encoding, and the widths must be computed under WinAnsi. |

| `embed-shared-descriptor.pdf` | Two differently-named non-embedded fonts through one `/FontDescriptor`. Both blocked. |
| `embed-std14-dingbats.pdf` | `/ZapfDingbats`, bare — the symbolic guard and the unspellable-encoding guard. |
| `embed-nometrics.pdf` | A non-standard-14 `/Type1` with neither descriptor nor `/Widths`. No metric source. |

## ★ Why `embed-std14-encoded.pdf` is a separate file rather than a variant

`StandardEncoding` and `WinAnsiEncoding` assign different glyph names to the
same code in more than a dozen places — `0o47` is `quoteright` under Standard
and `quotesingle` under WinAnsi, and the whole 0x80–0xFF region differs. A
`/Widths` array computed under the wrong one is wrong in the way that is
hardest to see: the page still looks right, the text is still selectable, and
the spacing is off by a few units per affected glyph.

Two fixtures that differ in exactly one dictionary entry make that mistake a
test failure instead of a shipped defect. This is the same reasoning
`existing_fixture_of_the_right_shape_can_be_vacuous_for_a_new_measurement.md`
records: a fixture that merely has the right *shape* does not exercise a
branch whose behaviour turns on a property the shape does not pin.

## ★ Where embedding deliberately diverges from unembedding

`embed-shared-descriptor.pdf` exists because the two operations are **not**
mirror images on this one point, and copying the mirror's rule across would
have been silently wrong.

`font_unembed` blocks a shared descriptor only when the other font is
*outside* the operation: two fonts sharing a descriptor and both being
unembedded is idempotent, because both remove the same `/FontFile*` key and
the second finds it already gone.

Embedding has no such property. Two font dictionaries with different
`/BaseFont` values resolve to two different donors, and one descriptor can
name only one `/FontFile2` — so whichever target ran last would win, and one
font would silently be drawn with the other's letterforms. `font_embed_missing`
therefore blocks **any** sharing, and this fixture is what proves the rule was
examined rather than inherited.

## What is deliberately NOT here

No fixture carries an embedded program that pdfcer then replaces. Replacing a
program a document already has is a *different* operation (font replacement,
still unbuilt — `docs/ROADMAP.md`), and a fixture for it here would suggest
this Pass covers it.
