# textblocks — provenance and attribution

One minimal PDF for Pass 14.0 (editable text model + block recognition,
`pdfcer_core::text_edit`), generated byte by byte by
`tools/gen-textblocks-fixtures.py`.

## Source material and license (LEGAL.md §5)

**Nothing here derives from a third-party file.** This is `LEGAL.md`
§5 category (a): **wholly synthetic**, authored for this project,
generated by a committed script with no PDF library behind it. No
embedded font programs, no third-party CMap resources, no corpus
material — so no attribution is owed and none is claimed. The content
is CC0-equivalent: placeholder English words ("Left column paragraph
one", …) carrying no expressive content, authored here for this test.

The absence of an embedded font program is deliberate and legally
clean: block recognition is a **second clustering pass over Pass 4's
extraction output**, and Pass 4's §9.10.2 ladder needs no font program
for the rungs pdfcer implements (a standard-14 Helvetica with
`/WinAnsiEncoding` resolves through Annex D.2 → AGL, both of which
`pdfcer-core` already carries). Positions come from pdfcer's own
standard-14 metrics, so the glyph geometry the recogniser clusters on
is exact and reproducible.

## Regenerating

```text
python tools/gen-textblocks-fixtures.py
```

Deterministic — no timestamps, no `/ID`, no random values. Running it
twice produces a byte-identical file, so it can be compared rather than
merely loaded. Requires nothing but a Python interpreter.

## The file

| File | The one thing it pins |
|---|---|
| `multi-column.pdf` | The whole **Run → Line → Column → Block** recognition pipeline (decision 014 §5.2's 13.0 slice). A two-column, four-paragraph, ten-line page in standard-14 Helvetica. **Lines:** ten separate `BT … Td (text) Tj ET` objects at known baselines, so Pass 4's derived line breaks (§14.8 **S5**) fall exactly where the recogniser must find them. **Columns:** two x-bands 250 units apart (left at x=72, right at x=322), content emitted left-column-first then right — so the fixture proves the left-to-right band **ordering** is by geometry, not content order (§14.8.2.3.1). **Blocks:** within each column a 28-unit leading gap (twice the 14-unit line leading) segments two paragraphs (§14.8 **S9**), for four paragraphs total. **Provenance:** the second left-column paragraph is painted blue (`0 0 1 rg`) and the rest black (unset default, then an explicit `0 g`), so the per-glyph fill-colour capture has a `Rgb`, a `None`, and a `Gray` to distinguish. |

## What must come out

Recognised from geometry alone (nothing is tagged):

- `columns = 2`, `lines_recognized = 10`, `blocks_recognized = 4`;
- `paragraph_breaks_by_leading = 2`, `paragraph_breaks_by_indent = 0`;
- blocks ordered left column (column 0) then right column (column 1);
- with provenance capture: every glyph's `font_resource = /F1`,
  `tf_size = 10`, `content_stream = Page`, and a real `Tj` operator
  span; the blue paragraph's `fill_color = Rgb(0,0,1)`.

## Uses

1. **Integration tests** — `crates/pdfcer-core/tests/text_edit.rs` and
   `crates/pdfcer-cli/tests/inspect_text_blocks.rs`.
2. **Manual demonstration** —
   `pdfcer inspect fixtures/synthetic/textblocks/multi-column.pdf --text-blocks`
   (add `--json` for the machine document).

## Not renderable-by-design caveats

This file **is** renderable (standard-14 Helvetica, `/WinAnsiEncoding`),
unlike some of the `../text/` fixtures — but rendering is not what it is
for. Its job is to exercise the derived block recogniser, which reads
glyph geometry, not pixels.
