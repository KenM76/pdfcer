# images — provenance and attribution

Raster-image fixtures for **image placement** — `pdfcer-core`'s
`image_import` module (PNG/JPEG/BMP → PDF image XObject),
`EditSession::add_image`, and the `pdfcer add-image` subcommand. Used by
`crates/pdfcer-core/tests/image_placement.rs` and by the unit tests inside
`crates/pdfcer-core/src/image_import/`.

## Source material and license (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** These are `LEGAL.md` §5
category (a): **wholly synthetic**, authored for this project, generated by
a committed script (`tools/gen-image-fixtures.py`) from pixel data this
project chose — flat colour ramps and index patterns, nothing derived from
any existing work. No attribution is owed or claimed, and no image was
downloaded from anywhere.

Every PNG and BMP is written **byte by byte** with the Python standard
library (`struct` + `zlib`), deliberately rather than through an imaging
library. The fixtures that pin the **passthrough** branch assert that pdfcer
reuses the source's compressed bytes *verbatim*, so those bytes have to be
bytes this project chose — a PNG produced by Pillow would carry Pillow's
choices about chunk order, per-row filter selection and compression level,
and the test would then be pinning Pillow rather than pdfcer.

The JPEGs are the exception: a JPEG needs a real entropy coder, so they are
encoded with **Pillow** (a developer-machine dependency only — never a pdfcer
dependency; verified with Pillow 12.1.0) from the same authored pixel data.
Two of them are then **patched** at the byte level, because no ordinary
encoder will produce them (see `arithmetic.jpg` below).

Regenerate with:

```
python tools/gen-image-fixtures.py
```

The script is not part of the build and is not a Cargo workspace member, so
it never enters the dependency graph or `THIRD_PARTY_LICENSES.md`.

## The shared pixel data

Every fixture is **6 × 4 pixels**. Small enough that a test can assert exact
sample values, large enough to have a distinguishable top/bottom (which is
what catches BMP's bottom-up row order and PNG's `Do`-onto-the-unit-square
orientation) and a non-square aspect ratio of 3:2 (which is what makes the
`Contain` / `Stretch` fitting distinguishable).

- **Colour ramp**: red rises 0 → 255 left to right, blue is its complement,
  green rises 0 → 255 top to bottom. So the top-left pixel is `(0, 0, 255)`
  and the bottom-right is `(255, 255, 0)` — a pair no symmetry can confuse.
- **Alpha ramp**: deliberately **not** binary. `alpha_at(x, y)` walks 0 →
  255 across the whole grid, because a 0/255 alpha would round-trip through
  a colour-key `/Mask` just as well as through an `/SMask`, and a fixture
  using it could not tell the two mechanisms apart.
- **Palette**: six entries — black, red, green, blue, yellow, white — indexed
  by `(x + 2y) mod 6`.

## What each file pins

### PNG — the verbatim-`IDAT` passthrough branch

| File | Pins |
|---|---|
| `rgb8.png` | Colour type 2, 8-bit, non-interlaced. **THE canonical passthrough case**: `/FlateDecode` + `/Predictor 15` + `/Colors 3` + `/BitsPerComponent 8` + `/Columns 6`, with the `IDAT` zlib stream copied byte for byte. Its rows use **mixed per-row filter tags** (None, Sub, Up, Paeth) — a passthrough that rewrote the rows would have to re-choose them, so identical tags are the cheapest proof the bytes were not touched. |
| `gray8.png` | Colour type 0 → `/DeviceGray`, `/Colors 1`. Also mixed filter tags. |
| `gray16.png` | Colour type 0 at 16 bits → `/BitsPerComponent 16`, a **PDF 1.5** feature; pins the version-ahead-of-document disclosure. |
| `indexed8.png` | Colour type 3, 8-bit indices → `[/Indexed /DeviceRGB 5 <lookup>]`. |
| `indexed4.png` | Colour type 3, **4-bit** indices → sub-byte packing, where `row_data_bytes = ceil(6 × 1 × 4 / 8) = 3` and `bpp = 1`. Pins that samples pack high-order-bit-first (§8.9.3 / RFC 2083 §7.2). |
| `rgb-trns.png` | Colour type 2 + `tRNS` naming one transparent colour (pure blue) → a colour-key `/Mask [0 0 0 0 255 255]` (§8.9.6.4), **with the passthrough preserved**. |
| `indexed-trns.png` | Colour type 3 + `tRNS` carrying **per-entry, non-binary** alpha (0, 64, 128, then implicit 255) → a decoded 8-bit `/SMask` while the indexed image data itself still passes through verbatim. |

### PNG — the decode-and-re-deflate branch

| File | Pins |
|---|---|
| `rgba8.png` | Colour type 6 → `/DeviceRGB` base + 8-bit `/SMask`. Mixed filter tags, so the un-prediction is exercised on all four non-trivial filters. |
| `graya8.png` | Colour type 4 → `/DeviceGray` base + 8-bit `/SMask`. |
| `rgba16.png` | Colour type 6 at 16 bits → a **16-bit** base and a **16-bit** soft mask. Pins that the mask keeps the source's precision rather than being quantised to 8 bits. |

### PNG — refusal

| File | Pins |
|---|---|
| `interlaced.png` | Adam7. Refused **by name** (`PNG/interlaced`): each pass restarts the predictor's `Prior(x) = 0` rule and PDF has no interlacing, so the `IDAT` cannot be reused and pdfcer has no de-interlacer. Built as a *legitimate* interlaced PNG (assembled pass by pass) rather than a file that merely sets the interlace byte, so that if a future Pass adds a de-interlacer the fixture is already a real test of it. |

### JPEG — the verbatim `/DCTDecode` branch

| File | Pins |
|---|---|
| `rgb.jpg` | Baseline SOF0, 3 components → `/DeviceRGB`. The headline byte-identity assertion runs on this one. |
| `gray.jpg` | Baseline SOF0, 1 component → `/DeviceGray`. |
| `progressive.jpg` | **SOF2.** 14% of the JPEGs measured inside real PDFs (decision 005 §3.2), so "baseline is enough" is false. §7.4.8 makes it legal from PDF 1.3; pdfcer embeds it unchanged and discloses NOTE 5's slower-decode caveat. |
| `cmyk.jpg` | 4 components with an Adobe APP14 marker whose **transform byte is 0** — R30's exact shape: nothing in the file declares the stored polarity. pdfcer embeds it unchanged, writes **no** `/Decode` (R29), and names the ambiguity. |
| `exif-rot90.jpg` | EXIF `Orientation` = 6 (rotate 90° clockwise), written as a hand-built minimal APP1/IFD0 so the bytes are exactly what this project chose. Pins that pdfcer applies the orientation in the **placement matrix** rather than re-encoding the pixels. |

### JPEG — refusal

| File | Pins |
|---|---|
| `arithmetic.jpg` | SOF9 (arithmetic entropy coding). Refused **by name** (`JPEG/arithmetic`). **Patched, not encoded**: libjpeg ships with arithmetic coding disabled and Pillow exposes no switch for it, so the only way to get this fixture is to rewrite the frame marker of `rgb.jpg` in place (byte offsets preserved). The entropy-coded data is then nonsense for an arithmetic decoder — which does not matter, because pdfcer must refuse it at the **marker walk**, before any decoder sees it. That is precisely the property under test. |

### BMP — the decode-and-deflate branch

| File | Pins |
|---|---|
| `rgb24.bmp` | `BI_RGB` 24-bit **bottom-up** — the Windows default, and half the world's BMPs. |
| `topdown24.bmp` | The same picture with a **negative** `biHeight` (top-down row order). Paired with `rgb24.bmp` in one test: both must import to identical PDF samples. A reader that ignores the sign silently mirrors the image vertically, which is a bug that looks like a bad source file. |
| `rgb32.bmp` | `BI_RGB` 32-bit whose fourth byte per pixel is deliberately **zero**. A `BITMAPINFOHEADER` bitmap has no alpha channel — that byte is padding — so a reader that treats it as opacity makes the image entirely invisible. |
| `pal8.bmp` | `BI_RGB` 8-bit with a 256-entry palette → `/Indexed`. Pins the BGRX → RGB palette rewrite and the 4-byte-stride → byte-stride repack. |
| `rle8.bmp` | `BI_RLE8`. Refused **by name** (`BMP/rle8`). |

### Not an image

| File | Pins |
|---|---|
| `not-an-image.bin` | A sentence. Refused **by name**, with a message that says which formats DO work. |

## Regeneration and stability

The fixtures are committed rather than generated at build time, so a change
to Pillow (or to Python's `zlib` compression) cannot silently move what the
tests assert. If `gen-image-fixtures.py` is re-run and a JPEG's bytes
change, that is a real event: the byte-identity assertions will still pass
(they compare the fixture against itself), but any test asserting *decoded
sample values* should be re-checked against a production PDF engine before
the new bytes are committed — **R31**, a reference decoder is evidence only
after its own conventions are verified.
