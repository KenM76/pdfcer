# outline — provenance and attribution

Ten minimal PDFs for the document-outline (bookmark) **reader** in
`crates/pdfcer-core/src/outline.rs` — ISO 32000-1:2008 §12.3.3 (the
outline hierarchy) and §12.3.2 (destinations). Each file isolates **one**
claim from that reader's contract, so a failing test names the clause it
broke rather than reporting that "bookmarks are wrong".

## Source material and license (LEGAL.md §5)

**Nothing here derives from a third-party file.** These are `LEGAL.md`
§5 category (a): **wholly synthetic**, authored for this project,
generated byte by byte by a committed script
(`tools/gen-outline-fixtures.py`) with no PDF library behind it — so the
fixtures cannot inherit a bug (or a normalization) from the very code
they test, and no attribution is owed or claimed. Every file uses a
classic §7.5.4 cross-reference table and US-Letter (612×792) pages with
no content streams: the outline is the entire subject, and page content
would only add bytes a test never reads.

Regenerate with:

```
python tools/gen-outline-fixtures.py
```

## Why hand-authored bytes, specifically

Most of what an outline reader must survive is something no authoring
tool will produce on request. A `/Next` chain that loops, a `/Count`
whose magnitude contradicts the tree, a destination naming an object that
is not a page, forty levels of nesting, an undefined PDFDocEncoding byte
in a title — every one of those is a *file a reader will meet* and none
of them is a file Acrobat, Word or LibreOffice will write for you. A
generator that emitted through a PDF library would have those
malformations normalized away before they reached disk, which is the
same argument `tools/gen-annot-fixtures.py` records for the annotation
corpus.

## What each file pins

### The structural rules (§12.3.3, Tables 152–154)

| File | Claim |
|---|---|
| `basic-tree.pdf` | The **happy path**, entirely well-formed: two chapters, five items, every `/Count` correct. `OutlineDiagnostics::is_faithful()` must be **true** — a diagnostic that is noisy on good files gets ignored on bad ones. Also carries the four `must_have` view types. |
| `lying-counts.pdf` | `/Count`'s **sign** decides open/closed; its **magnitude** decides nothing. Every count has the right sign and the wrong magnitude (`+9` on two children, `-7` on one, root `99`), so the two readings differ for every item. |
| `cycle.pdf` | Three distinct loops in one file. A reader without a cycle guard does not fail here — it **hangs**. |
| `deep.pdf` | Forty levels, past the reader's 32-level cap: a *reported* truncation, never a stack overflow. |
| `no-outline.pdf` | No `/Outlines` in the catalog. Empty and faithful, not an error — the overwhelmingly common real-world case. |

`basic-tree.pdf`'s counts are worth spelling out, because §12.3.3 gives
`/Count` two different meanings and the file is the executable statement
of both:

| Node | `/Count` | Rule |
|---|---|---|
| root | `4` | Table 152 — visible items at all levels, **including** the top-level ones: both chapters + Chapter 1's two children. Chapter 2 is closed, so its child contributes nothing. |
| Chapter 1 | `+2` | Table 153 — visible **descendants**, self excluded. Positive ⇒ open. |
| Chapter 2 | `-1` | Negative ⇒ closed; magnitude is what *would* become visible. |
| the four leaves | absent | *"Required if the item has any descendants"* — a leaf has none. |

### Destinations (§12.3.2, Table 151)

| File | Claim |
|---|---|
| `basic-tree.pdf` | `/Fit`; `/XYZ 72 720 null`; `/XYZ null null 2` (retain position, set zoom); `/FitH 700`; `/FitR 10 20 300 400` — pinning the `left bottom right top` order. Pages are objects 3–7 with indices 0–4, so an object-number/page-index confusion cannot pass. |
| `named-dests.pdf` | Both §12.3.2.3 namespaces and three of their edge cases — see below. |
| `broken-dests.pdf` | Three destinations that reach no page (a reference to a nonexistent object, a reference to the *catalog*, an empty array). All three keep their bookmark; none may vanish. |
| `both-dest-and-a.pdf` | One item carrying **both** `/Dest` and `/A`, which Table 153 forbids, pointing at **different pages** so the winner is provable rather than inferred. |
| `actions.pdf` | `/GoTo`; `/GoToR` by integer page number; `/GoToR` by name with a file-specification *dictionary* (`/UF` must beat `/F`); `/URI`; `/JavaScript`. |

`named-dests.pdf` in detail — the four ways a name is reached and the one
way it is not:

| Outline item | `/Dest` | What it exercises |
|---|---|---|
| Legacy intro | `/LegacyIntro` (a **name**) | PDF 1.1 catalog `/Dests` **dictionary** |
| Tree body | `(tree-body)` (a **string**) | PDF 1.2 `/Names → /Dests` **name tree**, reached through a `/Kids` interior node so the tree walk is genuinely exercised |
| Tree wrapped | `(tree-wrapped)` | the value is `<< /D […] >>`, not a bare array |
| Tree action | `(tree-action)` | the value wraps a **go-to action** instead of a `/D` — §12.3.2.3 NOTE 2's other permitted form |
| Crossed namespace | `(LegacyIntro)` | the legacy dictionary's key spelled as a **string**. Resolves only because pdfcer searches both namespaces regardless of the reference's type; pins the `DEST-A1` disclosure |
| Nowhere | `(nowhere)` | defined by neither namespace — kept as an unresolved name, not dropped |

### Text strings (§7.9.2, Annex D.3)

`titles.pdf` carries four `/Title` values, two of which are
silent-wrongness cases:

| Bytes | Correct reading | What a naive reader does |
|---|---|---|
| `Plain ASCII` | `Plain ASCII` | — |
| `FE FF 03BA 03B5 03C6` | `κεφ` | reads the bytes raw and renders mojibake |
| `A0 35 …` | `€5 fee` | assumes Latin-1 and renders a **no-break space** — plausible, wrong, and silent |
| `bad AD byte` | `bad\u{FFFD}byte`, flagged **inexact** | passes an undefined code through undisclosed |

`0xA0` is EURO in PDFDocEncoding, not NBSP; `0xAD` is one of the 24
undefined codes.

## Not covered here

Deliberately out of scope for this corpus, and named so a later session
does not assume they were tested:

- **Encrypted documents.** A `/Title` in an encrypted file is decrypted
  before the text-string layer sees it; that is `crate::document`'s
  contract, not the outline reader's.
- **Outlines in object streams (§7.5.7).** The reader works through
  `ObjectGraph` and cannot tell where an object was stored, so a
  compressed-object variant of every file would re-test the xref layer
  rather than this one.
- **`/SE`** (the structure element a bookmark corresponds to). Not read
  yet; needs a tagged-PDF fixture, which belongs with the tagging work.
- **Outline *authoring*.** Every file here is read-only input. The
  carryover rules for assembled documents have their own fixtures under
  `fixtures/synthetic/pageops/`.
