# `fixtures/synthetic/fontinfo/` — provenance

**Generator:** `tools/gen-fontinfo-fixtures.py`. Run it from the repo root:

```
python tools/gen-fontinfo-fixtures.py
```

Every file in this directory is reproducible from a clean checkout with that
one command and no arguments — the lesson `gen-encryption-fixtures.py`'s own
header records at length (a fixture whose construction nobody can repeat is a
fixture nobody can extend).

**Rights (project rule 7, `docs/LEGAL.md` §5):** every byte is synthetic and
self-authored. No real-world PDF of unknown provenance is present or was
consulted. The embedded font programs are the project's own
`fixtures/synthetic/text/subset-fstype-*.ttf` donors, themselves generated by
`tools/gen-subset-font-fixtures.py`.

**Consumed by:** `pdfcer_core::fontinfo`'s unit tests, and
`pdfcer`'s `list-fonts` integration tests.

## ★ Why the encrypted fixture lives here and not in `encryption/`

The Pass 67.0 brief named `fixtures/synthetic/encryption/enc-aes-128.pdf` as
the fixture that "has fonts and exercises the `data_span` hazard". **It does
not.** Its source document is `forms/demo-form.pdf`, whose only font is a
base-14 `/Helvetica` with **no embedded program at all** — so there is no
`/FontFile*` stream to measure and the hazard is never reached. A test written
against it would have passed vacuously, which is the worst outcome available:
a green assertion about a code path nothing executed.

`enc-aes-128-embedded-font.pdf` closes that gap. It is
`fixtures/synthetic/text/subset-simple-embedded.pdf` — which really does carry
a `/FontFile2` — encrypted by **pypdf**, an independent implementation. That
independence is the same argument `gen-encryption-fixtures.py` makes for the
rest of the corpus: agreement between pdfcer's spec-derived decryption and a
file pdfcer did not produce is evidence, whereas agreement with its own output
would be circular.

The hazard itself: `crates/pdfcer-core/src/document.rs`'s decryption walk
writes each stream's plaintext back at `data_span.start` and **shortens
`data_span.len`**, deliberately leaving the dictionary's `/Length` at the
ciphertext length. An `/AESV2` stream carries a 16-byte IV plus PKCS#7 padding,
so `/Length` overstates by at least 17 bytes. A font-size report built on
`/Length` is therefore wrong for every font in every encrypted document — and
plausibly wrong, which is worse than obviously wrong. The test asserts the
decoded program is byte-for-byte the same size as in the unencrypted source,
which only holds if the measured bytes were the plaintext.

## Note on `fontfile-type1.pdf`'s payload

The `/FontFile` stream's contents are **filler**, not a Type 1 font program:
a PostScript-looking header, a run of `A`s, a run of `0`s, and `cleartomark`,
with a `/Length1` `/Length2` `/Length3` split declared over them. Nothing in
pdfcer parses it as a font. The only assertions against it are its stored size,
its decoded size, and the fact that a Type 1 program has no `OS/2` table —
all three of which are true of filler. Writing a real Type 1 program to assert
those would add a font-format generator to this project for no additional
coverage.
