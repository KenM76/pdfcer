# shading — provenance and attribution

Single-page PDF fixtures pinning that **a shading and a flat fill of the same
authored `DeviceCMYK` ink render the same colour**. Generated by
`tools/gen-shading-ink-fixtures.py`; used by
`crates/pdfcer-render/tests/shading_ink.rs`.

## Source material and license (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** These are `LEGAL.md` §5
category (a): **wholly synthetic**, authored for this project, assembled byte
by byte from ISO 32000-1's own object syntax by a committed script. No
attribution is owed or claimed, and nothing was downloaded from anywhere.

**★ In particular, no byte of the licensed print-conformance suite is
reproduced here, and neither is its structure.** That suite is where the
operator *saw* the defect — a page whose shading boxes print a live shading
beside a reference image of what it should look like — but it is not
redistributable, it is not in this repository, and it is not present on a
fresh clone or on CI. These two files are the committed half of the evidence,
and they are deliberately **not** a reconstruction of that page: no reference
image, no four-up layout, a different colour, a different page size, and a
*constant* shading where the suite uses gradients.

The PDFs use a classic §7.5.4 cross-reference table with no object streams and
no compression anywhere, so a failing assertion can be diagnosed in a hex
editor and a fuzzer mutating one keeps producing something a parser engages
with.

## The two files

Both are 200 × 100 pt and draw the **same colour twice**: a flat filled
rectangle at (10, 20) 80 × 60, and an axial (`ShadingType 2`) shading clipped
to (110, 20) 80 × 60 whose `FunctionType 2` has `C0 == C1`.

| file | page group | what it pins |
|---|---|---|
| `shading-vs-fill-cmyk.pdf` | `/Group << /S /Transparency /CS /DeviceCMYK >>` | on a page that composites in **ink**, the two must be the same colour |
| `shading-vs-fill-rgb.pdf` | *(none)* | the **additive control** — they must match there too |

### ★ Why the shading is CONSTANT

A gradient cannot be compared against a flat fill without choosing a parametric
position and then arguing about whether the chosen pixel is really at `t = 0.5`.
A shading whose ramp is constant is the same colour **everywhere**, so any pixel
of it is comparable to any pixel of the fill, and the assertion needs no
geometry, no interpolation model and nothing remembered between runs. The
fixture is about *colour transport*, and the geometry is noise.

### ★★ Why the colour is `0.42 0.87 0.13 0.06` and not a primary

All four colorants are non-zero and the value is nowhere near a
`CMYK ↔ sRGB` fixed point. A round trip through sRGB moves it measurably —
**18 levels**, as the pre-fix A/B recorded. Pure cyan, or black, survives the
same round trip nearly intact and would have let the defect pass unnoticed;
a fixture that cannot fail is not a fixture.

### ★★★ Why the additive control is asserted at all

It passed before the fix and passes after, which makes it look like dead
weight. It is not: the additive page and the subtractive page are **different
code paths**, and without the control a future change that breaks the additive
one could hide behind the subtractive test staying green. The control's job is
to make that impossible, not to catch today's bug.

### What is deliberately NOT asserted

**That the two pages match each other.** A subtractive page converts out of ink
at the end; an additive one never entered ink. They are *required* to differ
wherever that conversion is not the identity. `shading_ink.rs` carries a third
test whose entire purpose is to stop somebody "tightening" the first two into a
cross-page equality that would be false for a correct renderer.

### What is NOT covered

**Mesh shadings** (types 4–7). `Shading::paint_cmyk` refuses non-analytic
geometry, so a mesh still bridges through sRGB and still disagrees with an
image of the same ink — a pre-existing, filed residual. When that is fixed, its
fixture belongs in this directory and its test in `shading_ink.rs`.

## An overprinting mixed-`/DeviceN` shading (Pass 201.0) -- two files

Written by `tools/gen-shading-ink-fixtures.py`; `LEGAL.md` SS5 category (a),
byte-authored, no PDF library involved. The colorant is named `/Spot Green` --
a generic name chosen here, not taken from any corpus.

`Pass 195.0` fixed a spot colorant's ink being DROPPED by widening a mixed
`/DeviceN` to write all four components. That wrote channels the source never
claimed, and its own comment said so while concluding "no patch in the
conformance corpus detects that". One does: a `1 0 1 .5 k` mark under such a
shading lost its `K = 0.5` and vanished, sixteen times on one page. **K is a
plane pdfcer has** -- so this was ink being ERASED by a fix for ink being
DROPPED, not the missing per-spot-colorant plane.

| File | Claim it makes falsifiable |
|---|---|
| `shading-overprint-mixed-spot-keeps-k.pdf` | A `1 0 1 0.5 k` rectangle under an axial `/DeviceN [/Spot Green /Cyan]` shading painted with `/OP true /op true /OPM 1`, whose tint transform writes C and Y and NEVER K. Table 149 must keep the backdrop's `K = 0.5`, so the band renders dark. Under `Pass 195.0`'s widening the source's `K = 0` is written instead and the two pages below become indistinguishable. |
| `shading-overprint-off-control.pdf` | * The control: the identical page with `/OP false`, where the source correctly DOES replace the backdrop and K goes to 0. Without it, "the band is dark" is equally satisfied by a build where the shading paints nothing at all -- which is what the spot-only refusal produces, one branch away in the same function. |

★ **Two things in these files are load-bearing and were each got wrong once
while authoring them**, recorded so the next author does not repeat them:

* **The page needs a `/Group` with `/CS /DeviceCMYK`.** Without a subtractive
  blending space pdfcer opens no colorant buffer, Table 149 never runs, and both
  pages render identically -- the fixture asserts nothing while looking fine
  (`cmyk_buffer=0` was the tell).
* **The shading's `/Function` and the colour space's tint transform are
  DIFFERENT functions.** The shading's maps the parametric `t` (one input) to
  the space's two components; the tint transform maps those two to CMYK.
  Handing the tint transform to the shading gives a two-input function one
  input, and the ramp comes out FLAT -- while still reporting
  `shadings_painted=1`.

Regenerate with `python tools/gen-shading-ink-fixtures.py`; the writer is
deterministic, so regenerating must be a byte-for-byte no-op.

## A spot shading and a spot fill of one tint (Pass 239.0) -- four files

Same oracle as the first two, one colour space over: a `/Separation /SpotGreen`
fill beside a constant-tint axial shading of the same `/Separation`, drawn with
`sh` or as a `/PatternType 2` shading pattern. Generated by
`tools/gen-shading-ink-fixtures.py`; wholly synthetic (`LEGAL.md` §5 category
(a)). Used by `crates/pdfcer-render/tests/shading_ink.rs`.

| File | Claim it makes falsifiable |
|---|---|
| `spot-shading-vs-fill-cmyk.pdf` | on white paper the `sh` shading and the fill agree -- pins "no double ink" (a route that both deposited AND flattened would differ), but CANNOT tell deposit from flatten: the plane's curve is sampled through the very conversion the flattened route takes |
| `spot-pattern-vs-fill-cmyk.pdf` | the same through a shading pattern |
| `spot-shading-op-over-k-vs-fill.pdf` | the DISCRIMINATOR: both boxes over a `0 0 0 0.5 k` mark under `/OP true`. A deposited spot leaves the K standing (Table 149, spot source x process colorant = `c_b`); a flattened one is a spot-only source the native route refuses, paints normally, and knocks the K out. The fill beside it deposits, so agreement means the shading took the plane. A sabotage that refused every shading its planes left the white-paper pair green and turned this pair red |
| `spot-pattern-op-over-k-vs-fill.pdf` | the same through a shading pattern -- the route the print-conformance suite's "shading" cells use, and the one that bridged through sRGB for pdfcer's whole life while `sh` had native ink routes |
