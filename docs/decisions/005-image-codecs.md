## 1. Context

`pdfce-core::filters` implements FlateDecode with PNG/TIFF predictors
and the two ASCII armouring filters. Everything else is *recognized and
refused* by name — the deliberate detect-don't-misparse posture from
decision 001 §6.1.4. That was correct for Pass 1. It is now the single
largest measured fidelity gap: the Pass 1.1 corpus run recorded
`images_unsupported` = 137 against `images_rendered` = 76. More images
are refused than drawn.

This record decides, per codec: which crate (or in-house), in what
order, where it plugs into the architecture, and how it gets fuzzed.

### 1.1 The constraints this decision has to serve

1. **Permissive licensing only** (`LEGAL.md` §6.1/§6.2). pdfce's own
   license is undecided (§1); a copyleft dependency is escalated to the
   user every time, never decided solo. This constraint does real work
   here — the mature JBIG2 and JPEG2000 implementations are GPL C
   libraries.
2. **Pure Rust, no C FFI.** Not an aesthetic preference: decision 003
   R11 makes the `wasm32-unknown-unknown` cross-check of `pdfce-core` +
   `pdfce-render` a first-class invariant guard, and `ARCHITECTURE.md`
   §6's single-folder portable packaging assumes no C toolchain and no
   runtime. `filter__jpx.md` states the consequence explicitly: an FFI
   binding triggers **both** the §6.2 license check on the underlying C
   library **and** reopens the portability question — flag both
   together.
3. **Adversarial-input posture** (`ARCHITECTURE.md` §10). These
   decoders eat hostile bytes by definition. Maintenance and fuzz
   history are selection criteria, not tie-breakers. Decision 004 §5.2
   set the precedent: `ttf-parser` was disqualified for a queue of
   unlanded security PRs, and the same logic applies to any codec with
   stale maintenance.
4. **Fail-clean is a type-level contract** (decision 001 §6.1.4,
   restated in `filters/mod.rs`'s header). Corrupt in → `Err` out.
   Never plausible-looking garbage. This is a deliberate divergence
   from the audited `oxidize-pdf`, which falls back to returning raw
   bytes.
5. **Fuzzy, never sneaky** (`CLAUDE.md` rule 4). An unimplemented codec
   feature is a named, counted diagnostic — never a grey box.
6. **Minimal dependency bloat**, with attribution generated by
   `cargo-about` (`LEGAL.md` §6.3).
7. **MSRV 1.92, toolchain pinned at 1.97.1**, edition 2024, resolver 3.
   The MSRV is already at the ceiling set by `eframe` 0.35 and has zero
   headroom.

### 1.2 The distinction this decision must preserve

**A byte-stream filter and an image codec are not the same kind of
object, and the existing API conflates them.**

`filters::decode_stream(dict, raw) -> Result<Vec<u8>, FilterError>` is
correct for Flate, ASCIIHex, ASCII85, RunLength and LZW: each consumes
bytes, produces bytes, and composes with the next stage of the cascade.

It is structurally wrong for DCT and JPX. §7.4.8's filter output is
*samples* whose interpretation depends on the JPEG's own internals —
component count, and the Adobe APP14 colour transform. §8.9.5 Table 89
goes further for JPX and **inverts the usual dictionary rules**:
`/ColorSpace` becomes optional and, when present, "any colour space
specifications in the JPEG2000 data shall be ignored"; when absent, the
codestream's own colour space is used and "the `Decode` array shall
also be ignored unless `ImageMask` is true"; `/BitsPerComponent` is
"optional and shall be ignored if present" because "the bit depth is
determined by the conforming reader in the process of decoding."

A `Vec<u8>` return type cannot carry any of that. Two more mechanical
facts point the same way: JBIG2 needs `/JBIG2Globals`, a **stream
reference** requiring `&Document`, which `(dict, raw)` cannot supply;
and CCITT needs `/Height` from the image dictionary when `/Rows` is 0
or absent.

§4.6 resolves this with a two-tier architecture. The distinction is
load-bearing enough to become a standing rule (R23), because "just add
DCT to the match arm in `decode_stream`" is the obvious wrong move and
it would work well enough for three of the five codecs to look right.

## 2. Options considered

### Decision A — DCTDecode (JPEG)
- **A1 — `zune-jpeg`** (zune-image project).
- **A2 — `jpeg-decoder`** (image-rs), the historical default.
- **A3 — the `image` crate** as a facade over whichever it uses.
- **A4 — `mozjpeg`/`mozjpeg-sys`** (C).
- **A5 — in-house.**

### Decision B — LZWDecode
- **B1 — `weezl`** (image-rs), the `PRIOR_ART.md` answer.
- **B2 — in-house**, ~200 lines against fully-sourced spec text.
- **B3 — `lzw`** (nwin), the pre-weezl crate.

### Decision C — CCITTFaxDecode
- **C1 — `hayro-ccitt`.**
- **C2 — `fax`** (pdf-rs), already in `Cargo.lock` via `tiff`.
- **C3 — the `tiff` crate's internal G3/G4 readers.**
- **C4 — `ccitt-t4-t6`**, or one of the 0.0.x newcomers.
- **C5 — in-house** from T.4/T.6.

### Decision D — JBIG2Decode
- **D1 — `hayro-jbig2`.**
- **D2 — `jbig2dec`/`jbig2dec-sys`/`nipdf-jbig2dec`** (C FFI).
- **D3 — `justbig2`.**
- **D4 — in-house** from T.88.

### Decision E — JPXDecode
- **E1 — `hayro-jpeg2000`.**
- **E2 — `jpeg2k`** (OpenJPEG C by default).
- **E3 — `openjp2`**, a machine-translated Rust port of OpenJPEG.
- **E4 — one of the 2026-vintage pure-Rust newcomers.**
- **E5 — defer JPXDecode indefinitely.**

### Decision F — architectural placement
- **F1 — extend `filters::decode_stream`** with all five codecs.
- **F2 — image-specific path in `pdfce-render`** beside `image.rs`.
- **F3 — a new terminal `image_codec` stage in `pdfce-core`**, with
  LZW alone staying in the byte-stream cascade.

## 3. Evidence

Two independent evidence streams were produced for this record: a
**corpus measurement run today over the 2,914 PDFs already staged in
`fixtures/external/`**, and **crate facts verified against the pinned
sources in the local cargo registry**, cross-checked against live
crates.io/GitHub data. Nothing here is recalled.

### 3.1 Which codecs actually appear, measured

Method: every `.pdf` under `fixtures/external/` (veraPDF-corpus +
pdf20examples, 2,914 files) was read as bytes and scanned for each
filter name. This is sound at the file level for image XObjects
specifically, because **a stream object can never live inside an object
stream** (§7.5.7), so an image's `/Filter` entry is always literal
bytes in the file.

| Filter | Files | Occurrences | Share of occurrences |
|---|---:|---:|---:|
| **DCTDecode** | **70** | **79** | **82.3%** |
| **LZWDecode** | 10 | 10 | 10.4% |
| **JPXDecode** | 7 | 7 | 7.3% |
| **CCITTFaxDecode** | **0** | **0** | 0% |
| **JBIG2Decode** | **0** | **0** | 0% |
| RunLengthDecode | 0 | 0 | 0% |

Method caveats, stated so the numbers are not over-read: names written
with `#`-escapes would be missed; inline images inside Flate-compressed
content streams are invisible to a raw scan; and the count is of
*stream declarations*, whereas `Diagnostics::images_unsupported` (137)
counts *`Do` invocations*, so one image XObject drawn on twenty pages
contributes once here and twenty times there. That difference is the
most likely explanation of the 96-vs-137 gap — stated as inference, not
fact.

**The two zeroes are the most important numbers in this table, and they
must not be read as "these codecs don't matter."** veraPDF and
PDF-Association corpora are hand-built to exercise structural
conformance. They contain no scanned documents, because nobody scans a
document to test an xref table. CCITT and JBIG2 are *exclusively*
scanned-document codecs. Their absence is a property of the corpus, by
construction. The real demand signal for them is `ROADMAP.md`'s OCR and
scanned-document Backlog buckets.

### 3.2 What shape those JPEGs actually are, measured

Every file containing `/DCTDecode` was walked marker-by-marker (SOI →
segment chain → SOS) and each codestream's SOF, precision, component
count, APP14 Adobe segment and DRI presence recorded. 70 codestreams
were found.

| Property | Result |
|---|---|
| **SOF0 baseline, 3 components** | **54 (77%)** |
| **SOF2 progressive, 3 components** | **10 (14%)** |
| SOF0 baseline, 1 component (grayscale) | 6 (9%) |
| Sample precision | **8-bit, all 70** |
| **4-component (CMYK/YCCK)** | **0** |
| Arithmetic-coded (SOF9/10) or lossless (SOF3) | 0 |
| **Adobe APP14 present** | **56 (80%)** — transform=1 ×50, transform=0 ×6 |
| **Restart intervals (DRI)** | **52 (74%)** |

Four consequences follow directly:

1. **"Baseline is enough" is false.** One in seven corpus JPEGs is
   progressive. A baseline-only decoder would leave 14% of the highest-
   value codec's instances unrendered.
2. **Restart-marker handling is not optional.** Three quarters of them
   carry DRI.
3. **The Adobe APP14 marker is the common case, not the exotic one.**
   80% carry it, which means the §7.4.8 `/ColorTransform` default rules
   — which depend on the marker's presence — are on the hot path.
4. **The CMYK question cannot be settled by measurement today.** Zero
   4-component JPEGs exist in this corpus. `filter__dct.md`'s hazard
   note (Adobe CMYK JPEGs "frequently stored inverted") is real-world
   producer behaviour that conformance corpora simply do not contain.
   §4.1 therefore designs for CMYK without *guessing* the inversion
   rule, and §9 makes the first real 4-component file a revisit
   trigger.

### 3.3 The DCT field, measured

`zune-jpeg` 0.5.15 and 0.4.21 are both present in the local registry;
the claims below were read from **`zune-jpeg-0.5.15/src/`**, not from
documentation.

| Crate | Latest | Released | License | `unsafe` | `no_std` | Deps | Verdict |
|---|---|---|---|---|---|---|---|
| **zune-jpeg** | **0.5.15** | 2026-03-26 | **`MIT OR Apache-2.0 OR Zlib`** | **`forbid` with SIMD off** | **yes** | 1 (`zune-core`) | **adopt** |
| `jpeg-decoder` | 0.3.2 | **2025-06-21** | `MIT OR Apache-2.0` | 7 files | **no** | 1 (`rayon`, opt) | reject |
| `image` (facade) | 0.25.10 | 2026-03-10 | `MIT OR Apache-2.0` | — | no | many | reject |
| `mozjpeg-sys` | 2.2.3 | 2025-01-21 | `IJG AND Zlib AND BSD-3-Clause` | C | no | C toolchain + nasm | reject |

The decisive line is `zune-jpeg-0.5.15/src/lib.rs:163`, verbatim:

```rust
#![cfg_attr(not(any(feature = "x86", feature = "neon")), forbid(unsafe_code))]
#![cfg_attr(not(feature = "std"), no_std)]
```

**With `x86` and `neon` off, the crate is `forbid(unsafe_code)` by
compiler attribute** — not by promise, not by audit. All 96 `unsafe`
occurrences live in 14 SIMD-intrinsic files that simply do not compile
in that configuration. This converts the usual "fast JPEG decoder =
lots of unsafe" tradeoff into an explicit, reversible switch, and it is
what makes A1 defensible under `ARCHITECTURE.md` §10.

The API is unusually well-shaped for a PDF filter, verified in
`src/decoder.rs`:

| Need | API |
|---|---|
| Validate geometry before allocating | `decode_headers()` → `info()` / `dimensions()` |
| Bounded, pre-sized decode | `output_buffer_size()` → `decode_into(&mut [u8])` |
| §7.4.8 `/ColorTransform` semantics | `input_colorspace()`, `output_colorspace()`, `DecoderOptions::jpeg_set_out_colorspace` |
| Resource ceilings | `set_max_width`, `set_max_height`, `jpeg_set_max_scans` |
| ICCBased reconciliation | `icc_profile()` |

APP14 handling is real and correct, `src/headers.rs:485-514`: `Adobe`
identifier check, transform byte → `0 => CMYK`, `1 => YCbCr`,
`2 => YCCK`. The 3-component/transform-0 ambiguity — where transform 0
means CMYK for four components but RGB for three — is resolved in
`src/misc.rs:209`, deferred until the SOF component count is known,
citing the Oracle JPEG-metadata documentation. Four components with no
APP14 default to CMYK (`src/headers.rs:256`).

Three limits are hard errors rather than silent approximations, which
is exactly what fail-clean needs: 12-bit precision
(`src/headers.rs:196`), and arithmetic-coded and lossless JPEG
(`errors.rs`: `UnsupportedSchemes::{ExtendedSequentialDctArithmetic,
ProgressiveDctArithmetic, LosslessArithmetic}`).

**The one real sharp edge**, found by reading `src/worker.rs`: the
`(input, output)` colourspace matrix is partial. `input == output` with
3 or 4 components short-circuits to a padding-removing copy — a genuine
raw-component passthrough, which is what §7.4.8's `/ColorTransform 0`
requires. `YCCK → RGB` and `CMYK → RGB` exist. **`YCCK → CMYK` does
not**, and falls through to
`Err(DecodeErrors::Format("Unimplemented colorspace mapping…"))`. An
error, not a panic — but it means pdfce must request YCCK passthrough
and do the YCC→CMY inverse itself. That is ~20 lines and it is the
right place for it anyway (R26).

Two further honest notes. `color_convert_ycck_to_rgb` computes
`blinn_8x8(255 - pix, K)` — i.e. it *assumes* the Adobe inverted
convention, which is sound because YCCK only ever arrives via APP14
transform 2. And an Adobe transform byte outside 0–2 is a **hard error
upstream**, where other readers tolerate it; §4.1 pre-sniffs APP14 so
that case becomes a named diagnostic instead of an opaque failure.

Independent corroboration: **the `image` crate 0.25.10 delegates JPEG
to `zune-jpeg`** (`jpeg = ["dep:zune-core", "dep:zune-jpeg"]`;
`jpeg-decoder` is gone from its dependency list), and **hayro — the
leading pure-Rust PDF renderer — also uses `zune-jpeg`** for
DCTDecode, with an explicit `unsafe` feature that flips
`zune-jpeg?/x86`. Two independent PDF/imaging projects converged on the
same crate *and* on the same feature-gating posture this record adopts.

### 3.4 LZW: the closest call in this record

| Option | License | `unsafe` | `no_std` | Fuzz | Maintenance |
|---|---|---|---|---|---|
| **`weezl` 0.2.1** | `MIT OR Apache-2.0` | **`forbid`** | yes (`alloc`) | **5 targets** | 2026-05-15 |
| in-house (~200 lines) | n/a | n/a | n/a | **none until we write it** | ours |
| `lzw` 0.10.0 | `MIT/Apache-2.0` | — | no | none | **2018-11-17** |

`filter__lzw.md` is the most complete file in the filter RAG: TIFF 6.0
§13 is quoted verbatim for code assignments (256 = Clear, 257 = EOI,
258+ = table), the 12-bit ceiling, MSB-first packing, the decoder's
510/1022/2046 thresholds, the KwKwK case, and the decoder pseudocode.
An in-house implementation is genuinely plausible — this was not a case
of the spec being unavailable.

`weezl`'s API maps onto `/EarlyChange` with no impedance at all:

| `/EarlyChange` | Meaning (Table 8) | `weezl` constructor |
|---|---|---|
| **1 (default)** | "code length increases shall occur one code early" | **`Decoder::with_tiff_size_switch(BitOrder::Msb, 8)`** — docs: "compatible with the TIFF specification… **It switches one symbol sooner**" |
| 0 | "postponed as long as possible" | `Decoder::new(BitOrder::Msb, 8)` — "compatible with the original specification" |

Two independently-sourced documents agree on that mapping: the RAG's
derivation from TIFF 6.0 §13's decoder text, and weezl's own
documentation. `BitOrder::Msb` is PDF/TIFF packing; `Lsb` is GIF's, and
`filter__lzw.md` already records that GIF LZW is structurally
incompatible.

`Decoder::decode_bytes(inp, out) -> BufferResult` decodes into a
caller-sized buffer, which makes `MAX_DECODED_LEN` enforceable
**incrementally** — the exact discipline `filters/mod.rs` already
promises for Flate ("abort mid-decode when crossed, never
inflate-then-check"). LZW's 1365:1 best case makes it a decompression-
bomb vector comparable to Flate, so this is not a nicety.

### 3.5 CCITT, JBIG2 and JPX: one vendor, three codecs

The `hayro` workspace (`LaurenzV/hayro`, "A PDF interpreter and
renderer in pure Rust", 727 stars, pushed 2026-07-29, PR numbering past
#1330) publishes eleven crates. Three are standalone codecs, all
`Apache-2.0 OR MIT`, all pure Rust:

| Crate | Ver | Released | `unsafe` | `no_std` | Deps | Downloads |
|---|---|---|---|---|---|---|
| **hayro-ccitt** | 0.3.0 | 2026-03-15 | **`forbid`** (+ `forbid(missing_docs)`) | **unconditional** | **0** | 656k |
| **hayro-jbig2** | 0.3.0 | 2026-04-12 | **`forbid`** | yes | 1 (`hayro-ccitt`) | 656k |
| **hayro-jpeg2000** | 0.4.0 | 2026-06-14 | **forbidden crate-level** | yes | 0 required | 550k |

Their APIs are PDF-shaped because they were written for a PDF renderer:

- **`hayro-ccitt`'s `DecodeSettings`** carries `columns`, `rows`,
  `encoding`, `end_of_block`, `end_of_line`, `rows_are_byte_aligned`,
  `invert_black` — a **1:1 map onto ISO 32000-1 Table 11**, including
  the `K`-sign trichotomy as `EncodingMode::{Group3_1D, Group3_2D{k},
  Group4}`. Its `Decoder` trait (`push_pixels`, `next_line`) is a
  *sink*, so rows land directly in pdfce's own 1-bit buffer with the
  ceiling checked per row.
- **`hayro-jbig2`'s `Image::new_embedded()`** takes optional global
  segments. That **is** the `/JBIG2Globals` path (Table 12). No
  general-purpose JBIG2 decoder exposes it.
- **`hayro-jpeg2000`'s `ColorSpace`** is
  `{Gray, RGB, CMYK, Unknown{num_channels}, Icc{profile,
  num_channels}}` — precisely the shape §8.9.5 Table 89 demands, where
  the codestream's colour space overrides the dictionary and an
  embedded ICC profile must reach the caller. `has_alpha()` is the
  `/SMaskInData` hook.

`hayro-fuzz/fuzz_targets/` carries `fuzz_ccitt.rs`, `fuzz_jbig2.rs` and
`fuzz_jpeg2000.rs`. None of the three is on OSS-Fuzz; neither is
`zune-image` (only `image-rs` is, which reaches `zune-jpeg`
transitively). `hayro`'s `NOTICE.md` attributes adapted code from
PDFBox, pdf.js and the `png` crate — and **lists nothing for the CCITT
or JBIG2 crates**, which is evidence they are original implementations
rather than ports of the GPL `jbig2dec`.

**The alternatives, and why none of them survives:**

- **CCITT — `fax` 0.3.0 (MIT, pdf-rs).** The strongest rejected
  candidate in this record. 35M downloads, three fuzz targets, written
  by the pdf-rs author explicitly for `CCITTFaxDecode`, already in
  `Cargo.lock` via `tiff`, actively committed this month. It loses on
  four small margins that compound: `deny(unsafe_code)` rather than
  `forbid`; **no `no_std`** (a live risk to the R11 wasm32 invariant);
  20% documented; and a non-PDF-shaped API that would leave pdfce
  hand-rolling Table 11 dispatch, byte-alignment and `BlackIs1`
  polarity — moving bug surface *out of* a fuzzed dependency and *into*
  our own glue. It stays named as the fallback.
- **CCITT — the `tiff` crate.** `Group3Reader`/`Group4Reader` are
  private internals with no standalone entry point, TIFF-shaped
  `fill_order` and dimensions, and they drag in
  flate2/zune-jpeg/weezl/half/quick-error. `tiff` is a *wrapper over
  `fax`* — depend on the codec, not the container.
- **CCITT — `ccitt-t4-t6`.** MPL-2.0 (weak copyleft → `LEGAL.md` §6.1
  escalation) and untouched since 2020-11-23.
- **JBIG2 — `jbig2dec` / `jbig2dec-sys` / `nipdf-jbig2dec`.** All three
  are **GPL-3.0 C FFI bindings** to Artifex's jbig2dec, and the two
  originals have not been touched since **2020-12-27**. Disqualified
  three times over — copyleft, C FFI, abandonment. Not escalated to the
  user, because `hayro-jbig2` removes the question rather than posing
  it.
- **JBIG2 — `justbig2`.** Four releases across two days in March 2026,
  then silence; 1,105 downloads.
- **JPX — `jpeg2k`.** Its default feature set is `openjpeg-sys` — C.
  A pure-Rust `openjp2` backend exists but is not the default, and
  `jpeg2k` has not shipped in a year.
- **JPX — `openjp2`.** A machine-translated Rust port of the C
  OpenJPEG, 4 stars. A transliteration inherits the C code's bug
  classes without the C code's fuzz history.
- **JPX — `j2k`, `oxideav-jpeg2000`, `rust-j2k`, `justjp2`,
  `pure_jpeg2k`.** All pure-Rust, all under ~1,500 downloads, all under
  five months old. Watch, do not adopt.

**A shadow family, flagged.** crates.io carries `pdfluent-ccitt`,
`pdfluent-jbig2`, `pdfluent-jpeg2000`, plus generically-named
`pdf-syntax`/`pdf-interpret`/`pdf-render`/`pdf-font`, all created
2026-05-02, all `Apache-2.0 OR MIT`, all with descriptions **byte-
identical to hayro's**, all pointing at `https://pdfluent.com/source`
rather than a public git host. Whatever their provenance, they are
unauditable. Named here so nobody reaches for them later by
name-similarity.

### 3.6 The dependency cost, and a correction worth recording

`Cargo.lock` already contains `zune-jpeg 0.4.21`, `zune-core 0.4.12`,
`weezl 0.1.12`, `fax 0.2.7` and `tiff 0.10.3`. The tempting conclusion
— "these are free, exactly like `skrifa` in decision 004" — **is
wrong**, and it was checked rather than assumed:

```
cargo tree -p pdfce-gui -i zune-jpeg  →  warning: nothing to print.
cargo tree -p pdfce-gui -i weezl      →  warning: nothing to print.
cargo tree -p pdfce-gui -i image      →  image v0.25.9
                                          ├── arboard v3.6.1 → egui-winit → eframe
                                          └── eframe v0.35.0
```

`image` **is** in the build graph (via `eframe` and `arboard`), but its
`tiff` and `jpeg` features are off, so `zune-jpeg`, `weezl` and `fax`
sit in the lock as **unenabled optional dependencies**. Confirmed from
the other side: `THIRD_PARTY_LICENSES.md` — generated by `cargo-about`
from the real build graph — contains **no** entry for `zune-jpeg`,
`weezl`, `fax`, `tiff` or `image`.

So the honest cost is **six new packages and six new attribution
entries**. What *is* free: the versions are already resolved (no new
resolution risk), and **every license is already in `about.toml`'s
accept-list** — `MIT`, `Apache-2.0`, `MIT OR Apache-2.0 OR Zlib`,
`Apache-2.0 OR MIT`. **Zero copyleft. No `LEGAL.md` §6.2 escalation
required for any of the five.**

The general lesson generalizes past pdfce and is dispatched to
`D:\dev\rag\rust\` in §10: **a crate in `Cargo.lock` is not
necessarily in the build graph.** Verify with `cargo tree -i`, never
with `grep Cargo.lock`.

## 4. Decision

### 4.1 DCTDecode — **A1, `zune-jpeg = "0.5"`, SIMD off**

```toml
zune-jpeg = { version = "0.5", default-features = false, features = ["std"] }
```

`default-features = false` drops `x86` and `neon`, which is what
activates `forbid(unsafe_code)`. `std` is kept: `pdfce-core` is a std
crate and `wasm32-unknown-unknown` supports std.

**The colour contract, stated as a table**, because §7.4.8 is the part
of this record most likely to be implemented wrongly. pdfce requests
the codec's *own* colour model in every case except the one fast path,
and then does its own reconciliation:

| SOF components | APP14 | `input_colorspace()` | pdfce requests | Result handed to render |
|---|---|---|---|---|
| 1 | any | `Luma` | `Luma` | 1 grey sample/px |
| 3 | absent, or transform=1 | `YCbCr` | **`RGB`** | zune applies the T.81 YCbCr→RGB transform (the §7.4.8 default) |
| 3 | transform=0 | `RGB` (after the `misc.rs:209` fixup) | `RGB` | passthrough, untransformed |
| 3 | `/ColorTransform 0` in `DecodeParms` | `YCbCr` | **`YCbCr`** | **passthrough** — the 3-component `input == output` short-circuit gives genuinely untransformed samples, which is precisely what `/ColorTransform 0` means |
| 4 | absent, or transform=0 | `CMYK` | `CMYK` | passthrough, 4 raw samples |
| 4 | transform=2 | `YCCK` | **`YCCK`** (passthrough) | pdfce applies YCC→CMY itself, because zune has no `YCCK → CMYK` arm |
| any | transform > 2 | — | — | pdfce pre-sniffs APP14 and emits a named diagnostic instead of letting zune hard-error |

The `/Decode` array is **never** applied here, and no "Adobe
inversion" is applied here. Both belong to `pdfce-render`'s existing
§8.9.5.2 machinery (R26). The inversion question is left genuinely open
rather than guessed at — see §5.5.

Ceilings are set explicitly: `set_max_width`/`set_max_height` derived
from `MAX_IMAGE_PIXELS`, `jpeg_set_max_scans` against the
progressive-scan bomb, and `output_buffer_size()` checked against
`MAX_IMAGE_PIXELS` *before* allocating, then `decode_into` a pre-sized
buffer.

### 4.2 LZWDecode — **B1, `weezl = "0.2"`, in `filters::lzw`**

The one codec in this record that stays a **byte-stream filter** inside
`decode_stream`'s cascade, because that is exactly what it is: bytes in,
bytes out, composable, and `/Predictor` applies to its output through
the existing `filters::predictor` module unchanged.

`/EarlyChange` maps to the constructor choice (§3.4 table).
Fail-clean behaviours, all sourced: a stream not starting with
`ClearCode` initializes the table anyway and counts a diagnostic; a
missing `EndOfInformation` terminates on input exhaustion without
erroring; corrupt mid-stream is `Err`.

### 4.3 CCITTFaxDecode — **C1, `hayro-ccitt = "0.3"`**

`fax` is the named fallback, and is worth keeping as a differential
oracle in the out-of-workspace `tools/difftest` if CCITT correctness
ever becomes contested.

**Blocking prerequisite:** Table 11's defaults for `/Columns`,
`/EndOfBlock` and `/BlackIs1` are flagged NEEDS VERIFICATION in
`filter__ccitt.md` — recalled, not read. `BlackIs1` is a polarity flag;
a wrong default inverts every fax image in a way that looks
deliberate. §10 dispatches the verification.

### 4.4 JBIG2Decode — **D1, `hayro-jbig2 = "0.3"`**, `default-features = false, features = ["std"]`

Ships in the same Pass as CCITT: `hayro-jbig2` depends on
`hayro-ccitt`, so they are one dependency decision, one vendor, one
review. `Image::new_embedded()` carries `/JBIG2Globals`. §7.4.7 and
§8.9.7 forbid JBIG2 in inline images, so the inline path **rejects**
rather than routes it.

### 4.5 JPXDecode — **E1, `hayro-jpeg2000 = "0.4"`**, `default-features = false, features = ["std"]`

`simd` off (it pulls `fearless_simd`, which is where the unsafe lives)
and `image` off (it pulls the `image` crate and `moxcms`, neither of
which belongs in `pdfce-core`).

This is the only codec here with a forced choice: `hayro-jpeg2000` is
the sole credible pure-Rust JPEG2000 decoder, at 550k downloads against
~1.9k for the nearest pure-Rust rival. Its upstream is honest about
gaps ("some missing pieces for some obscure features, like support for
progression order changes in tile-parts"), which R27 turns into named
diagnostics.

### 4.6 Placement — **F3, a two-tier filter architecture, both tiers in `pdfce-core`**

**Tier 1 — `filters::decode_stream`, unchanged in shape.** Byte-stream
filters only: Flate, ASCIIHex, ASCII85, RunLength, and now LZW.
Chainable. It gains one thing: a new
`FilterError::ImageCodec(String)` variant, returned when the chain
reaches a terminal image codec — "this is a codec, decode it through
the image path" — replacing today's misleading `UnsupportedFilter`.

**Tier 2 — new `pdfce_core::image_codec`.**
`decode_image(doc, dict, raw) -> Result<CodedImage, ImageCodecError>`
runs the byte-stream *prefix* of the `/Filter` chain through tier 1,
then dispatches the single terminal codec. It returns samples **plus
codec-declared geometry and colour model** (§6.3).

**Why `pdfce-core` and not `pdfce-render`.** Both crates are equally
covered by the wasm32 and GUI-free invariants, so the invariants do not
decide it; the consumer set does. `pdfce-cli`'s future
`extract-images`/optimize subcommands and the round-trip writer's
pass-through logic both need to *understand* image streams without a
rasterizer. `pdfce-render` already depends on `pdfce-core`, so it loses
nothing. And the split stays legible: **core decodes and models, render
paints.**

`pdfce-render/src/image.rs` keeps everything it owns today — sample
unpacking, `/Decode` per §8.9.5.2, colour-space resolution, `Indexed`
palettes, stencil masks, RGBA texels. Only its input changes, from
`filters::decode_stream` to `image_codec::decode_image`. The inline-
image path (§8.9.7, `/DCT` and `/CCF` abbreviations) routes to the same
entry point.

## 5. Rationale

### 5.1 Why the corpus zeroes did not set the priority order alone

The naive reading of §3.1 is "CCITT and JBIG2 score zero, so cut them."
That would be a measurement error dressed as data. veraPDF's corpus
exists to test structural conformance; nobody contributes a scanned
invoice to it. The codecs that score zero are precisely the codecs used
by the document class the corpus excludes.

So the order is set by corpus frequency **where the corpus is
representative** (DCT ≫ LZW ≫ JPX, all three being ordinary
digitally-authored content) and by **roadmap dependency** where it is
not: CCITT and JBIG2 are the precondition for the OCR and scanned-
document Backlog buckets, and they ship together in Pass 2.2 because
one vendor supplies both and `hayro-jbig2` depends on `hayro-ccitt`.

JPX ranks last for three converging reasons, not one: rarest at 7
files, the largest codec surface, and the most *unverified spec*
surface — Table 89's inversion of the dictionary rules plus an
unverified `/SMaskInData`. Its prerequisite work is the largest, its
payoff the smallest.

### 5.2 Why F1 is wrong even though it would mostly work

Adding all five codecs to `decode_stream`'s match arm is the obvious
move, and it would work for LZW, CCITT and JBIG2 — three of five —
because those genuinely produce PDF-shaped byte streams (packed 1-bit
rows for the fax codecs).

It fails on DCT and JPX for a reason that is structural rather than
inconvenient. §8.9.5 Table 89 makes a JPX image's `/BitsPerComponent`
"optional and… ignored if present" because "the bit depth is determined
by the conforming reader in the process of decoding," and makes
`/ColorSpace` optional with the codestream winning when both are
present. A function returning `Vec<u8>` has **nowhere to put the bit
depth or the colour space it just discovered**. The caller would have
to re-parse the codestream to recover what the decoder already knew —
i.e. parse hostile input twice, which is precisely the pattern
`ARCHITECTURE.md` §10 exists to prevent.

Two mechanical facts point the same way and would each independently
force a signature change: JBIG2 needs `&Document` to resolve
`/JBIG2Globals`, and CCITT needs `/Height` from the image dictionary
when `/Rows` is absent.

F2 (put it all in `pdfce-render`) fails for a different reason: it
would put image decoding behind the rasterizer, so `pdfce-cli
extract-images` and any future optimize/downsample Pass would either
depend on a rasterizer they do not need or reimplement the decode.

### 5.3 Why `weezl` beats a 200-line in-house LZW

This was the closest call in the record, and the arguments for in-house
are real: the spec is fully sourced, the code is small, and pdfce
already hand-rolls the ASCII filters and the predictors.

Three things decide it the other way. First, **`forbid(unsafe_code)`
plus five cargo-fuzz targets plus 114M downloads** is a fuzz history no
new implementation can have on day one, and `ARCHITECTURE.md` §10 makes
adversarial-input hardening a selection criterion rather than a
post-hoc activity. Second, **weezl 0.2.1's release note is "Fix:
overflow into low codes in burst derive"** — a real LZW correctness bug
found by someone else, in code we would otherwise have had to write and
then discover it in. Third, `decode_bytes(inp, out)` makes the
incremental `MAX_DECODED_LEN` enforcement natural, where a
Vec-growing in-house loop makes it something you have to remember.

The counter-argument — one more crate in the trusted computing base —
is answered by weezl's shape: zero required dependencies, one job, two
modes, and the two modes are exactly PDF's two `/EarlyChange` values.

### 5.4 Why SIMD stays off, and why that is a rule rather than a default

`zune-jpeg` without `x86`/`neon` is `forbid(unsafe_code)`. `hayro-*`
without `simd` pulls no `fearless_simd`. Turning those on buys decode
speed and costs the strongest safety property available in the Rust
ecosystem — a compiler-enforced absence of unsafe — in code whose
entire job is to consume attacker-controlled bytes.

pdfce has no measurement saying the safe paths are too slow. "Measure
before optimizing" applies with unusual force here, because the thing
being traded away is not elegance but a memory-safety guarantee.

R24 makes it a rule rather than a default for one specific reason:
**Cargo feature unification is transitive and silent.** If any crate
anywhere in the graph ever enables `image`'s `jpeg` feature, and that
path enables `zune-jpeg`'s `x86`, then pdfce's JPEG decoder quietly
stops being `forbid(unsafe_code)` with no diff to review. The CI check
must therefore assert the *feature state*
(`cargo tree -p pdfce-core -e features`), not merely the dependency
list. hayro's own `unsafe` feature — which flips `zune-jpeg?/x86`,
`hayro-jbig2?/simd` and `hayro-jpeg2000?/simd` together — is both the
precedent for how to expose this later and the demonstration of how
easily it travels.

### 5.5 Why the CMYK-inversion question is left open on purpose

`filter__dct.md` records the hazard: Adobe-produced CMYK JPEGs embedded
in PDFs are frequently stored **inverted**, and correct handling
interacts with the image's `/Decode` array. It also says, correctly,
that this is **empirical producer behaviour, not spec content**.

Three facts constrain what this record may honestly do about it. The
corpus contains **zero** 4-component JPEGs, so there is nothing to
measure. `zune-jpeg` reports `input_colorspace() == CMYK` both for "the
APP14 marker said CMYK" *and* for "four components with no APP14 at
all" (`headers.rs:256`), so the crate's API alone cannot distinguish
the two cases. And the spec's own mechanism for polarity is the
`/Decode` array, which real Acrobat output frequently does carry.

Guessing a rule now — "invert when APP14 is present" — would be
exactly the failure mode `CLAUDE.md`'s claim-verification rule exists
to prevent: a plausible convention adopted in place of a sourced fact,
in code where being wrong produces a photographic negative that looks
deliberate.

So: pass raw CMYK samples through, let `/Decode` do its documented job,
add a counter for 4-component DCT images so the case is *visible* the
first time it occurs, and make the first real file a revisit trigger
(§9). pdfce pre-sniffs APP14 in its own adapter — thirty lines of
marker walking, the same walk §3.2's measurement used — so the
transform byte is available to the rule *when there is a sourced rule
to apply*.

### 5.6 Why the vendor ceilings must be overridden rather than inherited

`zune-core`'s `DecoderOptions::default()` sets `max_width` and
`max_height` to `1 << 14` = **16,384**. That is a sensible default for
a general image library and a **bug** for pdfce: a 20,000-pixel-wide
scanned engineering drawing is legal, is under `MAX_IMAGE_PIXELS`
(32 Mpx), and would be refused.

This project has now been bitten by guard-by-intuition twice —
`MAX_TOKEN_LEN` at 8 KiB rejected a *valid* veraPDF file, and
`MAX_XOBJECT_DEPTH` at 16 rejected a conformant 32-deep chain. Both
incidents produced the standing rule that every new guard gets a run
against veraPDF's §6.1.12 implementation-limits suite. This would be
the third occurrence with a new twist: **the bad guard would be
inherited rather than written**, and would therefore never appear in a
diff as a number anyone chose.

R25 makes the override explicit and mandatory, and puts codec ceilings
under the same §6.1.12 validation as pdfce's own.

### 5.7 Why the license question stays closed

Every crate here is permissive and already covered by `about.toml`'s
accept-list: `MIT OR Apache-2.0 OR Zlib` (zune-jpeg, zune-core),
`MIT OR Apache-2.0` (weezl), `Apache-2.0 OR MIT` (the three hayro
codecs). Pass 0's "all permissive, ZERO copyleft" property survives
intact and **no `LEGAL.md` §6.2 escalation to the user is required**.

That outcome was not free — it is what the rejections bought. The
mature, obvious implementations of two of these codecs are GPL C
libraries: `jbig2dec` (Artifex) for JBIG2, and OpenJPEG-based bindings
for JPEG2000. Under `LEGAL.md` §6.1, with pdfce's own license still
open under §1, adopting either would have meant escalating a decision
that constrains §1 itself. `hayro-jbig2` and `hayro-jpeg2000` make the
question moot rather than answering it — the same move decision 004
made by choosing the BSD Foxit fonts over the AGPL URW set.

### 5.8 The concentration risk, named rather than hidden

Three of five codecs come from one author's project. `hayro` is
healthy by every visible measure — 727 stars, commits today, PR
numbering past #1330, dual-licensed, `forbid(unsafe_code)` throughout —
but it is one person's project, and pdfce would be depending on it for
CCITT, JBIG2 and JPX simultaneously.

The honest mitigation list is short and worth writing down before it is
needed: the crates are small, independently versioned, permissively
licensed and therefore forkable/vendorable; `fax` (MIT) is a working
CCITT fallback; and for JBIG2 and JPX **there is no permissive
pure-Rust alternative at all**, which is the actual exposure. If hayro
stops, pdfce's options for those two narrow to vendoring the last
release or writing T.88/T.800 decoders in-house.

## 6. What this decision produces

### 6.1 Standing rules (binding; add verbatim to `ROADMAP.md`, continuing R1–R22)

- **R23 — Image codecs are a terminal stage, not byte-stream filters.**
  `filters::decode_stream` never decodes DCT/CCITT/JBIG2/JPX; it
  returns `FilterError::ImageCodec(name)`. Codec output crosses the API
  as a `CodedImage` (samples + declared geometry + declared colour
  model), never as a bare `Vec<u8>`. `LZWDecode` is a byte-stream
  filter and stays in the cascade.
- **R24 — Codec crates are built with SIMD and unsafe features OFF.**
  `zune-jpeg` without `x86`/`neon` is `forbid(unsafe_code)` by compiler
  attribute; `hayro-*` without `simd` pulls no `fearless_simd`. CI
  asserts the **feature state**, not just the dependency set, because
  feature unification is transitive and silent. Enabling any SIMD
  feature requires a NEW decision record, a measurement showing it
  matters, and fuzz coverage of the enabled path.
- **R25 — Every codec ceiling is set explicitly by pdfce, never
  inherited from a vendor default.** `zune-jpeg`'s default 16,384-pixel
  dimension cap would reject legitimate wide scans. Ceilings derive
  from `MAX_IMAGE_PIXELS` and get a veraPDF §6.1.12 run before
  shipping.
- **R26 — The codec layer never decides colour.** `pdfce-core` hands
  `pdfce-render` the codec's own samples and its declared colour model.
  Only `pdfce-render` applies `/Decode` (§8.9.5.2), resolves
  `/ColorSpace`, and reconciles the two. No codec adapter may apply a
  `/Decode` array, an "Adobe CMYK inversion", or any polarity flip of
  its own — with one named exception: CCITT's `/BlackIs1`, which is a
  Table 11 *filter parameter* and therefore belongs to the adapter.
- **R27 — Unsupported codec sub-features fail clean and are counted BY
  NAME.** Arithmetic-coded JPEG, 12-bit JPEG, lossless JPEG, an unknown
  Adobe transform byte, a JPX progression-order change in tile-parts:
  each is a distinct named diagnostic. Never a grey box, never a
  guessed pixel, never a generic "decode failed."
- **R28 — Image encoders enter only under a decision record (005, 192, 193).**
  Shipped: JPEG, Flate, RunLength, CCITT G4, JBIG2 generic, LZW. pdfcer never
  *chooses* LZW. It is written only when named explicitly, never by a preset,
  `auto` or a fallback, and it is refused under a PDF/A claim.
  *(Amended 2026-10-21, decision 193: narrowed. The original text was "Read-compat
  only: pdfce writes none of these codecs. No image encoder enters any pdfce crate
  without a new decision record. LZW specifically is never written under any future
  decision — §7.4.4.1 NOTE 1 makes Flate strictly better on every axis but encode
  speed. Same posture as RC4 in the encryption bucket." The RC4 parallel was
  itself narrowed to "never chooses" by decision 190.)*

### 6.3 The API seam

```rust
// crates/pdfce-core/src/image_codec/mod.rs

/// A decoded image as the CODEC describes it — before any PDF-level
/// interpretation.
///
/// This type exists because §8.9.5 Table 89 lets the codestream
/// override the image dictionary for JPXDecode (`/ColorSpace` optional
/// and ignored-if-the-codestream-disagrees; `/BitsPerComponent`
/// "optional and shall be ignored if present"), and because §7.4.8's
/// DCT samples carry a colour model that depends on the JPEG's own
/// APP14 marker. A `Vec<u8>` return would discard exactly the
/// information the caller cannot recover without re-parsing hostile
/// input a second time.
///
/// Nothing here has had `/Decode` applied, and nothing here has been
/// colour-converted (decision 005 R26). That is `pdfce-render`'s job.
#[non_exhaustive]
pub struct CodedImage {
    /// Interleaved samples, row-major, row 0 at the top, packed per
    /// `bits_per_component` with rows padded to a byte boundary
    /// (§8.9.3) — the same layout the byte-stream filters produce, so
    /// `pdfce-render`'s existing unpacking path is unchanged.
    pub samples: Vec<u8>,
    /// Width in samples AS THE CODESTREAM DECLARES IT. May disagree
    /// with `/Width`; the caller decides (§6.4 counts the divergence).
    pub width: u32,
    /// Height in samples as the codestream declares it.
    pub height: u32,
    /// Components per sample as the codestream declares it.
    pub components: u8,
    /// Bit depth as the codestream declares it. For JPX this is
    /// authoritative and `/BitsPerComponent` is ignored (Table 89).
    pub bits_per_component: u8,
    /// The colour model the samples are actually in.
    pub color_model: CodecColorModel,
    /// An ICC profile carried inside the codestream, if any (JPEG
    /// APP2 / JPX `Icc`). Reconciled against `/ColorSpace` by the
    /// caller; never applied here.
    pub icc_profile: Option<Vec<u8>>,
    /// Alpha carried inside the codestream (JPX `/SMaskInData`).
    pub embedded_alpha: Option<Vec<u8>>,
    /// Per-image honesty counters (§6.4).
    pub notes: CodecNotes,
}

/// The colour model of `CodedImage::samples`, as the codec declares
/// it — NOT a PDF colour space. Mapping this onto `/ColorSpace` is
/// `pdfce-render`'s job (R26).
#[derive(Copy, Clone, PartialEq, Eq, Debug)]
#[non_exhaustive]
pub enum CodecColorModel {
    /// One component per sample.
    Gray,
    /// Three components, already transformed to RGB.
    Rgb,
    /// Three components, NOT transformed — `/ColorTransform 0`.
    Untransformed3,
    /// Four components in CMYK order, RAW: no `/Decode` applied and no
    /// "Adobe inversion" applied. See decision 005 §5.5 — pdfce does
    /// not guess the inversion rule.
    Cmyk,
    /// Bit depth 1, one component. CCITT and JBIG2 land here.
    Bilevel,
    /// The codestream declares a component count pdfce has no PDF
    /// mapping for. Never rendered; counted (R27).
    Unknown { components: u8 },
}

/// Decode an image stream through its `/Filter` chain.
///
/// Runs the byte-stream PREFIX of the chain through
/// [`crate::filters::decode_stream`], then dispatches the single
/// terminal image codec. `doc` is needed to resolve `/JBIG2Globals`
/// (Table 12) and to fall back to the image dictionary's `/Height`
/// when CCITT's `/Rows` is absent or zero.
///
/// # Errors
///
/// Never panics on any input (the fuzz targets in §6.5 assert this).
/// Every failure is a structured [`ImageCodecError`] naming the codec
/// and the specific unsupported feature where one applies (R27).
pub fn decode_image(
    doc: &Document, dict: &Dict, raw: &[u8],
) -> Result<CodedImage, ImageCodecError>;

/// Which terminal codec a `/Filter` chain ends in, if any — so callers
/// can route without decoding. The inline-image path uses this to
/// REJECT JBIG2Decode and JPXDecode outright (§7.4.7, §8.9.7).
pub fn terminal_codec(dict: &Dict) -> Result<Option<Codec>, FilterError>;
```

### 6.4 Diagnostics additions (R27, extending R20's disclosure discipline)


### 6.5 The fuzz plan

**Principle: fuzz pdfce's adapters, not the vendors' cores.** Every
vendor crate here already carries its own cargo-fuzz targets
(`weezl` ×5, `fax` ×3, `hayro-fuzz` ×3, `zune-jpeg` ×3), and
`zune-jpeg` additionally gets transitive OSS-Fuzz coverage through the
`image-rs` project. Our bugs will not be in their Huffman tables; they
will be in **the glue** — dictionary-vs-codestream geometry
reconciliation, buffer sizing for `decode_into`, row stride and
polarity for the bilevel codecs, ceiling enforcement, and colour
routing. That is what these targets aim at.

| Target | Status | What it asserts |
|---|---|---|
| `content_and_filters` | **extend** | Add `LZWDecode` in **both** `EarlyChange` modes, with and without `/Predictor`, over the same fuzzed bytes. LZW is byte-stream shaped exactly like the Flate/ASCII cases already there. |
| `image_codec_dct` | **new** | `decode_image` with a `/DCTDecode` dict over fuzzed bytes: geometry reconciliation, `output_buffer_size` → `decode_into` sizing, the colour-routing table of §4.1, the APP14 pre-sniff. |
| `image_codec_ccitt` | **new** | **Must fuzz the PARAMETERS as well as the data** — `K` (all three sign cases), `Columns`, `Rows` (including 0/absent → dict `/Height`), `EncodedByteAlign`, `EndOfBlock`, `BlackIs1`, `DamagedRowsBeforeError`. The parameter cross-product is where fax geometry bugs live. Use `arbitrary` to derive the parameter dict from the same input. |
| `image_codec_jbig2` | **new** | Includes the globals path: valid globals, absent globals, and globals that do not match the page segments. |
| `image_codec_jpx` | **new** | Table 89's inversion: dicts with `/ColorSpace` present and disagreeing with the codestream, `/BitsPerComponent` present and wrong, both absent. |

Invariant asserted by all five, identical to the existing targets: **for
any input, every call returns `Ok(_)` or a structured error — never a
panic, never an abort, never an unbounded allocation.** Seed corpora
come from `fixtures/synthetic/` only; never from a downloaded
real-world PDF (`LEGAL.md` §5).

The `fuzz-smoke` CI job gains the four new targets in its build check.

## 8. Consequences

**Good.**

- The largest measured fidelity gap closes: 137 refused images against
  76 drawn becomes, after Pass 2.3, a number that should round to zero
  on ordinary documents.
- **Every dependency is permissive**, so Pass 0's "all permissive, ZERO
  copyleft" property survives and `LEGAL.md` §1 stays open and
  unconstrained. Two of the five codecs had GPL C libraries as their
  obvious answer; neither had to be escalated.
- **Every codec is `forbid(unsafe_code)` in the configuration pdfce
  builds** — a compiler-enforced property, in exactly the code that
  eats hostile bytes.
- Every codec is `no_std`-capable, so the wasm32 fork premise survives
  intact; none needs a C toolchain, so single-folder portable packaging
  is unaffected.
- The two-tier split makes `pdfce-cli extract-images` and the future
  optimize/downsample Passes cheap, and it keeps the byte-stream filter
  contract — which is genuinely good and genuinely tested — unchanged.
- Priority order is set by a measurement anyone can re-run, not by
  intuition.

**Costs and risks, honestly stated.**

- **Six new packages and six new `THIRD_PARTY_LICENSES.md` entries.**
  This is not the zero-cost `skrifa` situation of decision 004, and
  §3.6 explains why the lockfile made it look like one.
- **Three of five codecs come from one author's project** (§5.8). For
  JBIG2 and JPX there is no permissive pure-Rust alternative at all.
- **`hayro`'s MSRV is exactly pdfce's**, with zero headroom.
- **The CMYK-inversion question ships unresolved** (§5.5), by design,
  with a counter instead of a rule. Someone will eventually meet a
  4-component JPEG and find pdfce's output inverted; the counter and
  the revisit trigger are what make that a five-minute diagnosis
  instead of a bug hunt.
- **`zune-jpeg` has open correctness issues** (#409, #362, #361, #273,
  #236) and hard-errors on an Adobe transform byte other readers
  tolerate. The adapter's own fuzz target and the APP14 pre-sniff are
  the mitigations, not a claim that the crate is flawless.
- **The safe (non-SIMD) decode paths are slower**, by an unmeasured
  amount. If large scans feel sluggish, R24's process — measure, then a
  new decision record — is deliberately a speed bump.
- **Pass 2.2 ships on zero corpus pressure.** That is defensible
  (§5.1), but it is a decision to build against a *roadmap* signal
  rather than a *measured* one, and it should be re-checked the moment
  an organic corpus exists.

## Addendum 2 — 2026-07-31 (decision 006 returned): the first addendum's count was wrong and its inference was FALSE

Recorded when decision 006
(`docs/decisions/006-cmyk-jpeg-inversion.md`) landed. The first
addendum (2026-07-30, above) is left as written — this second addendum
corrects it; do not edit it in place.

**Count correction (006 §3.1).** The first addendum reported **12**
four-component DCT instances. Two independent raw-byte scans of all
2,914 corpus PDFs (different anchors, so a bug in one would not
reproduce in the other) both find **9 instances / 2 distinct JPEG
payloads / 9 containing PDFs** (in `PDF_A-2b` and `PDF_A-4`, one page
each — no multi-draw inflation). The figure 12 could not be reproduced
by either scan and should be re-derived or retired (006 §10 item 10).
All 9 are homogeneous: baseline 8-bit, 300×232, Adobe APP14 present,
**transform byte 2 (YCCK) on every one**, `/DeviceCMYK`, no `/Decode`,
no `/DecodeParms`.

**Inference FALSIFIED (006 §3.2).** The first addendum inferred that
under §5.5's no-guess posture "these 12 files likely render inverted
today." **They do not.** pdfce pixel-matches pdfium (via `pypdfium2`
page renders — ground truth per R31) on **all 9 files**: mean Δ per
channel ≤ 0.5, sign agreement about mid-grey 100%, no polarity
difference of any kind. pdfce's `ycck_to_cmyk_in_place` replicates
libjpeg's `ycck_cmyk_convert` to within YCbCr rounding; the YCCK
inverse recovers true ink directly (TN #5116 §13.1 defines the forward
transform in terms of true ink values), so no further inversion step
exists to take. The "Adobe inversion" folklore lives exclusively in
the transform-0/no-marker raw-CMYK branch — of which the corpus
contains **zero** files.

**§5.5's no-guess posture was CORRECT, not merely cautious.** The
plausible guess §5.5 declined to make — "invert when the APP14 marker
is present" — would have **broken all 9** currently-correct files
(006 §5.6). Four production engines (pdf.js, pdfium, MuPDF's PDF path,
Poppler) implement exactly the never-invert rule; marker-gated
inversion was shipped and reverted twice upstream (cairo issue 156,
Firefox bug 674619). The open question this record's §5.5 carried is
now **closed by decision 006**: standing rules R29–R31, R26 made
permanent-and-sourced. No behavioral change was needed — the
deliverables are the rule, a split diagnostic
(`dct_cmyk_images` benign census / `dct_cmyk_polarity_unverifiable`
R30 warning), documentation, and six regression fixtures.
